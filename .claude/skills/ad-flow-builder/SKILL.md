# ad_flow builder — how to work here

`ad_flow` is a Flutter package that wraps `google_mobile_ads` (AdMob) into a clean, policy-compliant, revenue-optimized, easy-to-drop-in ad layer used across many of the maintainer's apps. This file is the operating manual. It is intentionally about **method, not facts** — the facts live in `docs/ad_flow_v2/RESEARCH.md`. Follow this method and a smaller model will produce the same quality as a larger one.

The prime directive: **the scarce, expensive resource is high-quality thinking. Spend it on the plan, the decisions, the architecture contract, and this skill — and capture all of it in files — so that whoever works next (possibly a smaller/cheaper model, possibly you with no memory of today) can continue at full quality.**

---

## 0. Orient before you touch anything (every session, no exceptions)

Before writing or changing a single line of code, read these files in this order:

1. `docs/ad_flow_v2/PROGRESS.md` — where we are, what's in progress, the exact next step.
2. `docs/ad_flow_v2/PLAN.md` — the phased plan and acceptance criteria.
3. `docs/ad_flow_v2/ARCHITECTURE.md` — the target architecture and the public-API contract you must implement to.
4. `docs/ad_flow_v2/DECISIONS.md` — why things are the way they are (don't relitigate settled decisions).
5. `docs/ad_flow_v2/RESEARCH.md` — ground-truth facts about `google_mobile_ads` 9.x, UMP, and AdMob policy.

If these files do not exist yet, you are at Phase 1: create them first (the master task prompt describes their contents). **Never skip orientation to "save time" — it is what makes a handoff safe.**

Precedence when they seem to conflict: **PROGRESS/PLAN** decide *what to do next*; **DECISIONS/ARCHITECTURE** decide *how*; **RESEARCH** decides *the facts*. If a real conflict exists, fix the docs first, then code.

## 1. The method

**Research-first — but don't re-research.** `RESEARCH.md` already contains the verified SDK/policy knowledge. Trust it. Go to the web only for something genuinely not covered there; when you do, **append what you learned back to `RESEARCH.md`** so the next worker inherits it instead of rediscovering it. Re-researching what's already written is the #1 way to waste scarce capacity.

**Isolate layers.** Build and change ONE layer at a time. The layers, bottom-up, are: **SDK seam → config → consent → policies → per-format controllers → lifecycle → facade → widgets.** A layer may depend only on the layers below it, and only through their interfaces. This is exactly what lets a smaller model work safely on one layer without holding the whole system in its head. If you find yourself needing to understand five layers to make one change, stop — the change is in the wrong place.

**Verify by running — always.** After every slice: `flutter analyze` must be clean and `flutter test` must be green **before you move on**. Do not reason about whether code is correct; run it. If you cannot run the tools in your environment, write down in `PROGRESS.md` exactly what must be run and stop at a safe point — do not guess and pile up unverified changes.

**Ship small vertical slices.** One controller, one policy, one widget per slice. Each slice: implement → write/adjust tests → `flutter analyze` → `flutter test` → update `PROGRESS.md` → commit. A slice should be small enough that its diff is easy to review and its tests obviously cover it. Never make a large, sweeping, untested change — it cannot be safely handed off.

**Never fabricate an API.** Use only `google_mobile_ads` 9.0.0 symbols documented in `RESEARCH.md`. If you are not certain a class/method/parameter exists, **grep the installed package source in the pub cache** (`find ~/.pub-cache -path '*google_mobile_ads*/lib/*.dart'`) and confirm before using it. A hallucinated API compiles in your head and fails on device — worse than pausing to check.

**Prefer deleting to adding.** This is a rewrite; reuse the *battle-tested logic* from v1 (retry timing, the consent-sample flow, test-mode) but not its global-singleton structure. When in doubt, the simpler design that satisfies the invariants wins.

## 2. Non-negotiable invariants (AdMob-specific — breaking these loses money or gets accounts banned)

These are not style preferences. Each one maps to real revenue or a real policy-enforcement risk. Never violate them, and add a test that guards each one.

1. **Consent gates every load.** Never call any ad `load()` before `ConsentGateway` reports `canRequestAds()` is true. `MobileAds.initialize()` may run in parallel with consent gathering, but no `load()` until the gate is open. Guard against double-loading with a boolean.
2. **Privacy options entry point.** When `getPrivacyOptionsRequirementStatus()` is `required`, a persistent "Manage consent / Privacy settings" control must be available that calls `ConsentForm.showPrivacyOptionsForm(...)`.
3. **App-open ads: warm-start only.** Never show on the first cold launch while still loading. Show only on foreground-return via `AppStateEventNotifier.appStateStream`. Enforce the **4-hour expiry** (discard + reload stale ads). Never show an app-open ad while another full-screen ad is showing (use the `FullScreenAdCoordinator`). Never over content that also shows a banner.
4. **Interstitials at natural breaks only.** Enforce a frequency cap (per-format time + count, and a global cross-format cap). Never on app launch or app exit; never immediately after another ad closes; never interrupt an active task.
5. **Rewarded interstitial: intro + skip first.** Always present the intro/announcement screen with clear reward messaging and a skip option before the ad plays. Non-negotiable AdMob policy.
6. **Test ads only in library/example code.** The library must never hardcode a production ad-unit ID. Production IDs come exclusively from `AdFlowConfig`. Keep a `testMode` that uses Google's official sample IDs.
7. **Single-use full-screen ads.** Interstitial / rewarded / rewarded-interstitial / app-open instances show once. Dispose them in the dismiss/fail callback and **reload the next one immediately** so one is always warm.
8. **The SDK seam is the only door to the plugin.** All `google_mobile_ads` calls go through `AdSdk`. Nothing else imports `google_mobile_ads` except the seam and the widgets that must host an `AdWidget`. This is what makes everything testable with `FakeAdSdk` and keeps the legacy/Next-Gen native swap invisible to our code.
9. **No global mutable state.** No static/singleton config. Config and collaborators are injected. A convenience accessor may exist, but it must be backed by an injectable instance so tests construct their own.

## 3. Definition of done for a slice

A slice is done only when ALL of these are true:

- It compiles and `flutter analyze` is clean (zero warnings/infos you introduced).
- Unit tests are written and green, using `FakeAdSdk` (and fakes for consent / key-value store / clock as needed). Every invariant the slice touches has a guarding test.
- Public API is documented with dartdoc comments.
- `DECISIONS.md` updated if you made any non-obvious choice (ADR entry: context → decision → rationale → consequences).
- `MIGRATION.md` updated if the public API changed relative to v1.
- `PROGRESS.md` updated (Section 4 template).
- Committed with a clear, scoped message (e.g. `feat(interstitial): add frequency-capped controller with reload-on-dismiss`).

If any of these is not true, the slice is not done — do not start the next one.

## 4. Handoff protocol (you may be replaced by a smaller model at any moment)

Assume that the next turn is a different model with **no memory of this conversation**. The only things it inherits are the repository and the docs. Make that enough.

End **every** session by updating `docs/ad_flow_v2/PROGRESS.md` using this template:

```markdown
# PROGRESS — ad_flow v2

## Current phase
<n> — <name>

## Done
- <completed slice> (<commit hash>)
- ...

## In progress
- <exact file(s)> — the very next concrete step is: <one sentence>

## Next (ordered)
1. <slice>
2. <slice>

## How to verify the current state
`flutter analyze` && `flutter test`   (or the exact narrower command, e.g. `flutter test test/policies/`)
Expected: analyze clean, N tests passing.

## Open questions / assumptions
- <anything a fresh model must know to not go wrong>

## Traps hit this session
- <new pitfall> → also append it to SKILL.md Section 6
```

Rules for a safe handoff:

- **Always leave the tree green.** Never stop mid-slice with a broken build or red tests. If you must stop, retreat to the last green state (or finish the tiny bit needed to make it green) first.
- **Never leave a half-fabricated API.** If you were unsure and guessing, revert the guess before you stop.
- **Front-load when capacity is low.** If you sense you are running out of room, do NOT start new work. Instead: (a) get the current slice to green, (b) update `PROGRESS.md`, (c) append any new trap to Section 6 of this skill. Those three things are what preserve quality across the handoff.
- A resuming model's first three actions are always: read the six docs (Section 0) → run `flutter analyze && flutter test` to confirm the green baseline → continue from `PROGRESS.md`'s "In progress".

## 5. When stuck

Do not thrash and do not silently guess. In order:

1. Re-read the relevant `RESEARCH.md` / `ARCHITECTURE.md` section — the answer is often already written down.
2. Confirm the API against the pub-cache source (grep it) rather than assuming.
3. If it's a genuine decision, make the **smallest safe assumption**, record it in `DECISIONS.md` (and note it under "Open questions" in `PROGRESS.md`), and continue.
4. If it's a decision only the maintainer (Faiz) can make, stop **at a green state** and ask him — never leave a broken build to "fix later."

A clean stop with a clear question beats a large, broken, speculative change every time.

## 6. Common pitfalls here (learned from v1 — append to this list whenever you hit a new one)

- **iOS `inactive` is NOT backgrounding.** v1 treated both `paused` and `inactive` as "went to background," so an app-open ad could fire after Control Center, a permission dialog, the notification shade, or the app-switcher preview. Use `AppStateEventNotifier.appStateStream` for the real foreground signal; do not hand-roll lifecycle detection off `didChangeAppLifecycleState`.
- **Don't fight the UMP callback API.** v1 wrapped UMP in `Completer`s + void callbacks + several 60s safety timeouts and still hit an "async-callback-as-void" bug. Wrap UMP into clean `Future`s **once**, in `ConsentGateway`, and let the rest of the code `await` it.
- **Test-mode detection must come from config, not resolved IDs.** v1 computed `isUsingTestAds` by checking whether the *resolved* ad-unit IDs contained Google's test publisher ID. Because unconfigured formats fall back to test IDs, a production app that simply didn't use one format falsely reported "using test ads." Derive test-mode from an explicit flag/config field.
- **One owner of app-open/foreground behavior.** v1 allowed two lifecycle reactors to exist (a widget-based one and an `enableAppOpenOnForeground` one) and coordinated them through static globals, which fight. Make two reactors impossible by construction; share suppression state through an injected `FullScreenAdCoordinator`, not statics.
- **Linear backoff hammers the SDK.** v1 retried on a fixed `delay * attempt` schedule with no jitter, so multiple managers retried in lockstep. Use exponential backoff **with jitter**, a max attempt count, a cooldown, and then **auto re-arm** (v1 also failed to re-arm banner/native loads after the cooldown unless the widget remounted).
- **No global frequency cap.** v1 only had a per-interstitial time cooldown. Real revenue/UX safety needs per-format time + count caps **and** a global cross-format cap so a user isn't hit by an interstitial then an app-open back to back.
- **The Flutter plugin has no preload API — even in 9.0.0.** "Preloading" is manual: `load()` ahead, cache the instance, `show()` later, and reload the next in `onAdDismissedFullScreenContent` / `onAdFailedToLoad`. Do not look for a `PreloadController`; it doesn't exist in Flutter.
- **Rewarded interstitial is not just a rewarded ad.** It needs the mandatory intro/skip screen; shipping it without one is a policy violation, not a UX nicety.
- **`dispose()` discipline.** Every `BannerAd`/`NativeAd`/full-screen ad and every stream subscription must be disposed. Lint with `close_sinks` / `cancel_subscriptions`; a leaked ad is a real memory and correctness bug.
- **app-ads.txt is required (since Jan 2025)** for full ad serving. It's a publisher-side setup step, but the README must call it out prominently or the maintainer's apps silently under-serve.
- **`AppStateEventNotifier.appStateStream` is dead until `startListening()`.** The plugin only starts emitting foreground/background events after `AppStateEventNotifier.startListening()` runs. `GmaAdSdk.appForegroundEvents` calls it lazily on first access — if you ever bypass the seam, remember it, or app-open-on-foreground silently never fires.
- **`BannerAd.isCollapsible` and inline-adaptive real height are async post-load calls.** `isCollapsible` is `Future<bool>`, and an inline adaptive banner's real height comes from `getPlatformAdSize()` after load. `GmaAdSdk` resolves both inside the load flow so `BannerHandle.size`/`isCollapsible` are plain sync getters above the seam.
- **`RequestConfiguration` tags are ints, not bools** (`TagFor*.yes/no/unspecified` = 1/0/-1; `maxAdContentRating` is a String constant). The seam maps `bool?`/enum → plugin encoding in `toGmaRequestConfiguration`; never pass raw bools through.
- **`MobileAds.updateRequestConfiguration()` runs SYNCHRONOUSLY on the platform thread; `initialize()` runs on a background thread. Never call the former before the latter completes — you will deadlock the platform thread on a cold device and freeze the whole app.** Verified in the plugin's own Android source: `MobileAds#initialize` → `new Thread(...)`, but `MobileAds#updateRequestConfiguration` is serviced inside `onMethodCall` on the UI thread and calls `MobileAds.get/setRequestConfiguration()`, which force the Play Services Ads-Dynamite settings-manager singleton (`ChimeraMobileAdsSettingManagerCreatorImpl`) to bootstrap on the platform thread — racing init's background bootstrap of the same singleton → deadlock → dead isolate (no first frame, no timer, no `.timeout()` fires). `AdFlow._start()` must `await initialize()` FIRST, then `updateRequestConfiguration()` (still unconditional / not consent-gated — finding #5, just ordered). This caused a **three-round misdiagnosis** as "native/environmental/unfixable" (ADR-027 + addenda) before someone read the *plugin's* source and found it (ADR-028). Lesson for §5: when a hang looks like it's "below our layer," read the collaborator's actual source to confirm *which thread* each call runs on before concluding it's unfixable — black-box diagnosis reached the right mechanism (synchronous platform-thread block stalls the isolate) but the wrong, defeatist cause.
- **A stale shader cache (`ink_sparkle.frag`) fails widget tests with "Unsupported runtime stages format version. Expected 2, got 1."** After a Flutter engine/artifact refresh (e.g. many `flutter run` rebuilds, or an SDK bump), the Material ripple shader baked into the last test build can go stale, and the *first* widget test that renders a button ripple throws this — looks like a real regression, isn't. Fix: `flutter clean && flutter pub get`, then re-run. Not caused by any source change.
- **Never build a banner/native controller inside `build()` — and `AdFlowBanner`/`AdFlowNativeAd` now defend against it.** `ads.banner()`/`ads.native()` each mint a *new* controller and start a *new* ad load. Calling them in `build()` means every `setState` hands the widget a fresh, unloaded controller; before hardening, `AdFlowNativeAd` (which loaded only in `initState`) then hosted a never-loaded controller forever — a permanent blank ad plus a leaked, still-loading old controller — while the banner reloaded wastefully. The tell in on-device testing: the ad blanks exactly when some *unrelated* `setState` fires (e.g. a coin counter updating after a reward), not on the ad's own activity transition. Create controllers once (in a `State` field / `initState`) and pass the stable instance. The widgets now also implement `didUpdateWidget` to adopt a swapped controller (dispose old if owned, load new) as a safety net — but the correct usage is still one stable controller per placement (ADR-029).
- **`AppStateEventNotifier` doesn't replay the cold-launch foreground.** `GmaAdSdk.appForegroundEvents` calls `startListening()` lazily, *after* the app is already foregrounded, so the initial ON_START is never delivered. **This means the first event the manager receives is a GENUINE warm return, and it now shows an ad on it (ADR-043).** ⚠️ This bullet used to say the opposite — that the manager "correctly suppresses it as a cold start" and that you must background→return *twice* on an emulator. That was **wrong**, and it cost one app-open impression in every session on both platforms for two releases. Verified on device (Android emulator + iOS simulator, 2.1.0): one background→return now shows the ad. Invariant 3 still holds, structurally: at a real cold launch nothing is loaded yet, so `show()` finds no warm ad. Do not re-introduce the latch.
- **Const asserts cannot compare `Duration`s.** `assert(minRefresh >= const Duration(seconds: 30))` in a const constructor fails with `const_eval_type_num` at every const call site (only `num` operands may be compared in const expressions). Validate/clamp Durations at use-time (controller) instead of in const constructors.
- **A synchronous check-then-`await`-then-write is not atomic — it's a race.** Any `if (_state.value is X) return; ... await something; ... _state.value = Y;` pattern lets two concurrent calls both pass the check before either writes, because the write happens *after* a yield point. This bit `load()` (double-load, leaked handle) and `show()` (double-show, `handle.show()` called twice on one single-use ad) in every full-screen/banner/native controller. Fix: write the guard state *synchronously*, in the same turn as the check, before the first `await` — then roll back if the subsequent async check fails.
- **A shared mutable resource (the `FullScreenAdCoordinator`) needs its own synchronous check-and-claim, not a synchronous write reached via someone else's async gate.** `AdGate.canShow`'s `if (coordinator.isFullScreenAdVisible) return false;` is itself synchronous, but it's *reached* through an `async` function (`canShow`), and `coordinator.enter()` was only called later, after `handle.show()` resolved. Two independent controllers (e.g. interstitial + app-open) could both read "not visible" in the same synchronous turn before either entered — both would show. The fix is a `tryEnter()` method ON THE COORDINATOR ITSELF (plain sync method, no `await` anywhere in it) that controllers call as their literal first action, bypassing the gate's own coordinator check entirely for the show() decision path. See DECISIONS ADR-024.
- **A load blocked by the gate (not failed by the SDK) needs its own re-arm, separate from retry-after-failure.** `RetryPolicy`'s cooldown-then-re-arm (ADR-008) only fires after an `AdFlowError` from `loadHandle()`/`_sdk.loadBanner()` etc. If `_gate.canLoad` itself returns false (ads disabled, consent not yet open), the controller used to just go idle with no timer — nothing ever tried again, even after the gate reopened. Every `load()` needs a `_scheduleGateRecheck()` parallel to `_scheduleRetry()`, reusing the same timer field.
- **A `StatelessWidget` reading a plain `bool` getter at build time cannot react to that value changing later.** `PrivacyOptionsButton` read `ConsentGateway.isPrivacyOptionsRequired` directly — correct at the widget's first build, permanently stale (and permanently hidden, if `false` at first build) once the value changes afterward, with nothing to trigger a rebuild. Any state a widget must reflect *whenever it becomes true*, not just *once at mount*, needs a `ValueListenable`/`ValueListenableBuilder`, not a getter — this is exactly ADR-005's "one reactive primitive" principle, and skipping it for one field is how invariant 2 (privacy options entry point) broke silently. See DECISIONS ADR-025.
- **`ValueNotifier`'s setter no-ops (skips `notifyListeners()`, and therefore skips the disposed-check) when the new value equals the current value.** Reading `.value` after `dispose()` never throws either — only a *write that actually changes the value* hits `ChangeNotifier`'s disposed assertion. A test asserting "this notifier is disposed" must force an actual value change, not just read `.value` or write the same value back, or it will silently pass for the wrong reason.
- **An explainer/intro presenter must be context-safe; the package never holds a `BuildContext`.** The consent/ATT priming screens (ADR-030) and the rewarded-interstitial intro (ADR-023) all use the *presenter* pattern — the package calls a `Future` callback and the *app* supplies the UI, resolving its own `navigatorKey.currentContext` inside the callback (`if (context == null || !context.mounted) return;`). Never pass a `BuildContext` into the package or store one in a controller/gateway — v1's `initializeWithExplainer(context:)` did, which is exactly what v2 removed. When you add any new package-initiated UI, follow the same shape: a `typedef …Presenter = Future<T> Function(Content)`, injected at `initialize`, invoked behind a guard, and a broken presenter must never block the underlying flow (catch it, record `lastError`, proceed to the real prompt/form). Also: a `capture?.call(show(...))` in a widget *test* short-circuits argument evaluation when `capture` is null (the `?.` guards the whole expression) — call `show(...)` first, then forward, or the screen never opens.
- **A nested `Future<Future<void>>` return type is illegal** (Dart flattens `Future<Future<void>>` because of `void`-flattening; `Future<Future<bool>>` compiles but `Future<Future<void>>` does not). A test helper that opens a `show(...) → Future<void>` primer can't `return` that future from an `async` helper typed `Future<Future<void>>`; capture it via a `void Function(Future<void>)` callback param instead.
- **Config-before-load (`updateRequestConfiguration`) is a SEPARATE requirement from the consent gate, and non-blocking init exposed that (ADR-033).** `AdGate.canLoad` gates on `canRequestAds()` (consent), which is independent of `MobileAds.initialize()`/`updateRequestConfiguration()`. Before ADR-032, `initialize()` returned only *after* `_start` applied config, so on-demand `ads.banner()`/`ads.native()`/`controller.load()` couldn't precede config by construction. Once init went non-blocking (ADR-032) and the example mounted a banner on the first frame, a non-EEA/returning user's fast `canRequestAds()==true` let that load fire while the slow cold-device init (and thus config) was still pending → an untagged/untest-flagged first request (review-fix #5 / COPPA regression). Fix: the gate itself must `await` a `configReady` future (completed after `updateRequestConfiguration`) before the consent check — so config-before-load is structural, not an accident of when `initialize` happened to return. Lesson: when you move work off the synchronous return path, re-check every ordering guarantee that the old synchronous return was *implicitly* providing (here: "the instance isn't reachable until config is applied"). An adversarial multi-agent review caught this; the finder that traced *both* load paths (preload AND on-demand) found it, the ones that only checked preloads missed it.
- **`AdFlow.initialize()` is NON-BLOCKING (ADR-032): it returns before consent, and startup runs in the background — never gate the first frame on it.** Graph construction is synchronous; `initialize` sets `_instance` synchronously, kicks `_start()` unawaited (errors captured — a background startup failure must never reach the caller), and returns immediately. The returned `Future<AdFlow>` completes on the next microtask, BEFORE consent. `await ads.whenReady` is the (optional) way to await the consent gate; do NOT make it required or gate UI on it, and do NOT wrap the app in a `FutureBuilder<AdFlow>` spinner (that reintroduces v1's splash hang). Consequences to remember when editing: (a) the ADR-027 30s init timeout now bounds `whenReady`/background `_start`, not `initialize` — tests asserting "initialize hangs when init hangs" must target `whenReady`; (b) the ADR-028 init→`updateRequestConfiguration` ordering lives INSIDE the background `_start`, still preserved; (c) `_start` must re-check `_disposed` after awaiting consent (a caller can `dispose()` mid-startup); (d) keep `initialize` `async` (not a sync `AdFlow` return) so a synchronous constructor throw stays a rejected Future and `await_only_futures` doesn't fire at every `await AdFlow.initialize()` site; (e) any test that used to assume "after `await initialize`, consent resolved + preloads happened" now needs `await ads.whenReady` (the `boot()` helper does this centrally).
- **The seam's "I only throw `AdFlowError`" contract is a LIE at runtime — catch `Object` on every degradation path (ADR-034).** A real platform channel throws `MissingPluginException`, `PlatformException` and bare `StateError`s (and so does `shared_preferences`). Every `on AdFlowError catch` in a *degrade-or-die* position is a wedge waiting to happen: a raw throw from `loadHandle()` escaped `load()` and pinned the slot at `AdLoading` — which `load()`'s own re-entry guard then rejects **forever**, with no retry armed; a raw throw from the ATT seam aborted the whole consent flow (no GDPR form, no privacy entry point, zero ads); a throwing frequency-cap store inside `show()` escaped with the `FullScreenAdCoordinator` still claimed, killing every full-screen format for the session. Rule: anything reached AFTER a coordinator claim or a synchronous state write must sit inside a `try` that rolls both back on ANY throw, and normalize through `asAdFlowError`. Losing one impression always beats wedging a format.
- **A plugin listener does NOT stop firing after the load completes — `onAdFailedToLoad` fires on every failed AdMob AUTO-REFRESH of the same `BannerAd`.** Review finding #2 caught the `onAdLoaded` half (a second success double-completed the load `Completer`) but left the symmetric hole: a *failed* refresh ran the full load-failure teardown against a LIVE, mounted ad — disposing it, closing the handle's streams (silently ending paid-event reporting for that placement) and calling `completeError()` on an already-completed Completer. Whenever you complete a `Completer` from a plugin callback, ask "can this callback fire again after the ad is live?" — for banners (and natives) the answer is yes. Guard with `if (completer.isCompleted) return;` and do NOT tear down a live ad.
- **The plugin's `InlineAdaptiveSize` has HEIGHT 0 until `getPlatformAdSize()` resolves it** ("an AdSize with the given width and 0 height", per the plugin's own source). A null/throwing `getPlatformAdSize()` therefore left a LOADED, BILLABLE ad rendered in a zero-height box — an impression the user can never see. Never fall back to the *requested* size for an inline adaptive banner; treat an unresolvable height as a failed load.
- **Non-blocking init (ADR-032) makes the consent gate a PROCESS, not a fact — and every consumer of it must treat it as one (ADR-035).** Two separate bugs came from reading it as a fact: (a) the consent flow ran exactly ONCE per session, so an offline launch left `canRequestAds()` false with nothing to re-ask → **zero ads for the whole session** even after the network returned; (b) a first-frame banner reached the gate before consent resolved (the config gate opens in ~1s with no user interaction; consent needs the network, and maybe an ATT prompt and a GDPR form a human must read), read a hard `false`, and re-armed only after `RetryConfig.cooldown` — **5 minutes** → blank banner/native through the first five minutes of every new install. Fixes: `AdGate.canLoad` awaits a `settleConsent` callback that JOINS the in-flight attempt and RE-ATTEMPTS a failed one; the gate re-check uses a short exponential backoff, not the failure cooldown. Distinguish **failed** (retry it) from **declined** (a settled answer — never re-prompt, `lastError == null` is the discriminator). Corollary for §5: when ADR-032 moved work off the synchronous return path it invalidated ordering guarantees *and* the assumption that one attempt is enough — re-check both.
- **A persisted timestamp from a device whose clock was AHEAD blocks every ad forever (ADR-037).** `now - last` goes negative, which is always `< minGap`, so one future-dated impression permanently blocked that slot and — via the global cap — EVERY full-screen format, across restarts, with no recovery short of clearing app data. Cheap handsets with a dead RTC boot to a garbage date until NTP lands (minutes, on a weak network), and users set the clock forward to skip in-app cooldowns. Any persisted-clock comparison needs a "this is in the future ⇒ it is garbage, ignore it" guard.
- **A package-supplied screen whose last child is a MANDATORY control must scroll (ADR-038).** The rewarded-interstitial intro, and both primers, were unscrollable centred `Column`s: on a 320x568 device at 200% text scale they overflowed by 128 / 704 / 1536 px, pushing the last child off-screen where it is ALSO not hit-testable. The rewarded intro's last child is AdMob's mandated **skip** option — so a text-scale setting turned a required opt-out into an unreachable one: a policy violation, not a UX nit. Localized copy is longer than English, so this bites well below 200%. Use `ExplainerBody` (centres when it fits, scrolls when it doesn't) for any new package screen, and test at a large `TextScaler` on a small view.
- **An adaptive banner is requested FOR a width, so it must be re-requested when the width changes (ADR-036)** — but ONLY when it actually changes. `AdFlowBanner` latched `_loadRequested` on the first layout and the controller cached a stale `_width`, so after a rotation the ad was letterboxed AND every subsequent refresh re-requested the wrong size. The guard is the load-bearing half: re-requesting on every rebuild would be an ad-request storm (invalid traffic). Compare the integer width; a keyboard opening changes height only.
- **When you write a fail-first test AFTER already touching lib/, you have not written a fail-first test.** Two of this session's fixes were coded before their tests ran red. Verify non-vacuity by reverting the behaviour (keep the API shape so it still compiles), running the new tests, and confirming they fail — then restore. One of the three "new" tests turned out to pass either way (it was a regression guard, which is fine) — you only learn that by checking.
- **`ValueNotifier` will not tell a widget that the ad HANDLE changed, because `AdLoaded == AdLoaded` (ADR-041).** The swap-on-refresh path replaces `controller.handle` while the state stays `AdLoaded`; `ValueNotifier`'s setter no-ops on an equal value, so a widget listening only to `state` goes on rendering the OLD, now-disposed handle — a dead ad, or a crash. Any time you replace a resource *without* changing the state enum that describes it, you need a second signal: `BannerAdController.revision` (an int notifier bumped on every swap), with the widget on `Listenable.merge([state, revision])`. Same root cause as the ADR-025 trap: the reactive primitive must carry *everything* the widget renders from.
- **When you delete a latch, every test that PRIMED that latch silently lies.** Removing the app-open cold-start latch (ADR-043) broke five tests that each began with `sdk.emitAppForeground(); // consume cold-start event` — they were not testing the latch, they were paying a toll to get past it, and with the toll gone their arithmetic was off by one ad. Grep for the *setup* line, not just the assertion, whenever you remove a gate: `grep -n "consume cold-start"` found all five instantly. The same applies to any "prime the pump" line in a test.
- **The "safe" direction is not automatically the correct one — check whether the thing you are guarding against can even happen (ADR-043).** For two releases the manager threw away its first foreground event to avoid showing an app-open ad on a cold launch, and §6 of this very file recorded that as intended and policy-safe. It was neither: `AppStateEventNotifier` never emits a cold-launch foreground at all (the seam calls `startListening()` *after* the app is foregrounded), so the latch was only ever eating a REAL warm return — one lost impression in every session, on both platforms, for a hazard that did not exist. Before defending against an event, confirm the platform actually delivers it. And prefer a *structural* guard to a counter: invariant 3 now holds because at cold launch no ad is loaded yet, which is a property of the system rather than a flag that can be wrong.
- **A cap that blocks a user-initiated ad is a bug, not a policy (ADR-039).** The global cross-format cap existed to pace ads the user did NOT ask for. Applied to a rewarded ad, it means a user taps "watch an ad for 100 coins" and gets no ad, no reward and no explanation — the highest-eCPM format in the package, refused by a 15s default gap. When a policy knob spans multiple formats, ask which of them the user *chose*, and split the knob. Note the asymmetry that makes it safe: rewarded impressions are still RECORDED globally (so an involuntary interstitial cannot fire straight after one) — the exemption is on the *block*, not on the *record*.
- **A gap timestamped at SHOW runs down while the ad is still on screen (ADR-040).** A 30s rewarded ad under a 15s gap consumed the entire gap before the user even closed it, so an interstitial could fire the instant they dismissed it — two full-screen ads back to back, which is precisely what the gap was there to prevent. "One ad every N seconds" means N seconds of *app*, not N seconds that an ad may itself eat. Record on dismiss (with a dispose/fail-to-show safety net, so a torn-down ad still counts).
- **A destroy-then-reload refresh is a blank slot, and on a weak network it is a blank slot for SECONDS (ADR-041).** Load the replacement in the background and swap only on success; a failed refresh must keep the perfectly good ad already on screen rather than take it down with it. Distinguish *failed* (keep the ad, back off) from *gate-closed* (Remove-Ads/consent withdrawn → the ad is no longer PERMITTED, so drop it). Also: do not duplicate a job the platform already does — AdMob refreshes banner ad units server-side, from the console, on by default, so a client-side refresh timer on top is a second unsynchronised loop and up to 2x the requests.
- **The plugin's `AdWidget` cannot re-point its platform view at a new ad — key the hosted subtree by handle identity (ADR-047).** `_AdWidgetState` has no `didUpdateWidget`; the platform view captures the ad id at creation, and Flutter only recreates a platform view when its `viewType` changes (never — one constant per plugin). Rebuilding with a NEW handle updates the element in place, so the screen keeps hosting the OLD (disposed) ad — a permanently dead slot that still requests fresh ads. `AdFlowBanner`/`AdFlowNativeAd` use `KeyedSubtree(key: ObjectKey(handle))`; any new widget hosting `handle.buildWidget()` must do the same.
- **A continuation that installs a resource after an `await` must RE-VALIDATE the world it captured (ADR-046).** The banner `_refresh()` captured `requestWidth` and the handle-to-replace, awaited the SDK, then swapped unconditionally — stomping whatever a concurrent resize-driven load had installed, leaking a live `BannerAd`, and (in its catch) cancelling a recovery timer another path owned. The ADR-024 rule ("write guard state synchronously before the first await") covers ENTRY races; this is the EXIT half: after the await, check `_disposed`, that the state is still the one you set out from, and reconcile anything (like `_width`) that moved while you were suspended — and only touch the shared `_timer` if the slot is still yours.
- **Verify non-vacuity by NEUTERING a fix with `git stash`, never `git checkout <file>`.** `git checkout` restores from the INDEX: if the fix is not yet committed/staged, it silently destroys the fix along with the neutering edit (cost a full re-implementation of the ADR-051 base changes this session). `git stash push -- <file>` / `git stash pop` round-trips safely.
- **Adding a member to a public `abstract interface class` is a breaking change for external implementers — prefer a delegating wrapper.** ADR-050 needed post-mutation hooks on the consent surface; adding them to `ConsentGateway` would have broken every app-side implementation, so `AdFlow.consent` returns a `_GraphAwareConsentGateway` wrapper instead. The seam handle interfaces DID gain members (`dimensions`, `response`, `updateServerSideVerification`, `recheckGate`) — acceptable because they are documented as implemented-by-the-package(+fakes) — but every such addition must be called out in the CHANGELOG's implementer note.
- **Extend the fuzz suite's op set when adding controller operations (ADR-054).** `state_machine_fuzz_test.dart` only defends against interleavings of the operations it knows; a new public method or timer on a controller must be added to the op tables or the net silently narrows.
- **A diagnostic must not be a new case in a `sealed` type.** Adding e.g. `AdBlocked` to `AdLoadState` would be the tidiest model and would break every exhaustive `switch` in every consuming app — a breaking change, unshippable in a minor. Put the information in a PARALLEL channel instead (`AdBlockReason` + `lastBlockReason` + an `onAdBlocked` callback, ADR-045). "Where does this information belong?" and "what does adding it there break?" are two different questions, and the second one decides.

- **A constructor-kicked lazy future lives in the CONSTRUCTION zone — a fakeAsync test can never drive it.** `StoredFrequencyCapPolicy` hydration kicked in the constructor (run in `setUp`, real zone) parked every `canShow` inside `fakeAsync` forever: fake_async only pumps its own zone's microtasks/timers. Any internal async warm-up a collaborator needs must be LAZY (`late final Future<void> _x = _run()`), created by the first call — in whichever zone the caller drives (ADR-060).
- **`await`ing a completed Future is a microtask, and microtask FIFO is what makes "record then check" ordered** — but do not rely on it: commit decision state SYNCHRONOUSLY before the first await (`recordImpression` applies memory before persistence), and let the returned future mean durability only.
- **Adding an enum case is a breaking change exactly like a sealed-type case** (exhaustive switches stop compiling). 4.0 added `AdBlockReason.internalError`/`requestConfigNotApplied` and `AdFlowErrorKind.ssv` — batched into a major deliberately. Never slip an enum case into a minor.
- **The plugin acks `setServerSideVerificationOptions` unconditionally** (`result.success` even on its logged null-ad branch, both platforms — verified 9.0.0 source). Client-side "SSV attached" can only ever mean "the channel did not fail"; never document it as confirmation. The SSV endpoint receiving the payload is the only proof.
- **The plugin has NO load timeout and never cleans up a load whose callback never arrives** (no timer anywhere in its load paths; `_loadedAds` entries removed only by dispose — verified 9.0.0 source). Every load await in ad_flow goes through `watchAdLoad` (`RetryConfig.loadTimeout`); keep new load paths on it.
- **"Config after init" is not enough — config after a TIMED-OUT init re-opens the ADR-028 deadlock.** The bounded wait returning is not the same as init completing; the native bootstrap may still be live on the platform thread. Key the dispatch off the ACTUAL completion (`_initDone` via `whenComplete`), never off "our timeout elapsed" (ADR-061).
- **A readiness/ordering invariant lives in WHEN you publish `AdLoaded`, not in how you gate `show()` (ADR-068).** Runtime SSV re-attached the override in a post-publish `onLoaded()` hook (unawaited), so the ad was briefly `AdLoaded`+showable carrying the stale payload — a state listener or an immediate `show()` used it, no matter how `show()` was gated. The only correct fix is to not publish `AdLoaded` until the handle is fully finalized: `finalizeLoadedHandle()` is `await`ed BEFORE the state write (throw → fail the load closed). Corollary: for concurrent updates to the same warm resource, generation-stamp each and let only the latest generation's completion resolve state — the method channel is FIFO natively, so the Dart-side guard only has to stop a stale completion (esp. a stale FAILURE) from clobbering the latest.
- **A `fakeAsync` `elapse` of hours against a CLOSED gate churns the gate-recheck retry densely and can look like a hang.** A blocked load arms `_scheduleGateRecheck` (exponential backoff capped at `maxDelay` ~1min), so `elapse(Duration(hours: 2))` with consent withdrawn fires ~120 re-check cycles — enough to spin a test for minutes (it is legitimate recovery behavior, not a code loop). Bound such elapses in tests (a few minutes), or assert the drop directly without a long elapse. Tell: the test's `flutter_tester` process pins ~30% CPU and never prints its `+N`.
- **A one-shot that must survive `AdFlow` reinitialization needs PROCESS-scoped state, which is invariant 9's second sanctioned exception (ADR-067).** The cold-launch App Open opportunity is once per process, not per `initialize()` — a reinit builds a new manager but must not mint a second launch show. That cannot be injected instance state, so `AppOpenAdManager._processLaunchOpportunity` is a `static final LaunchOpportunity`, allow-listed in `no_global_state_test` alongside `AdFlow._instance` and injectable (`launchOpportunity:`) for test isolation. When you genuinely need process-scoped state, add it to that allow-list with an ADR — do not hide it as a top-level `final` to dodge the guard.
