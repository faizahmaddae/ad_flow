# DECISIONS — ad_flow v2 (ADR log)

Architecture Decision Records. Each entry: **context → decision → rationale → consequences.** Settled decisions are not to be relitigated; if you must change one, add a new superseding ADR that references it. Append a new ADR whenever you make a non-obvious choice.

Status legend: `accepted` (agreed with the maintainer / by design), `proposed` (needs confirmation as you build).

---

## ADR-001 — Ground-up rewrite to v2  ·  accepted
**Context.** v1.3.18 is feature-rich and heavily tested but architecturally constrained: all-singleton, static global config, hand-rolled observer, a lifecycle bug, and pinned to `google_mobile_ads ^7.0.0` (two majors behind).
**Decision.** Rewrite from scratch as **v2**, reusing the *battle-tested logic* of v1 (retry timing, the consent-sample flow, test-mode) but not its structure.
**Rationale.** The problems are structural, not cosmetic; a clean architecture is cheaper than incrementally untangling global state.
**Consequences.** A new `lib/` tree; v1 code stays available in git history for reference; published as a new major.

## ADR-002 — Clean v2 public API + MIGRATION.md  ·  accepted
**Context.** The package is used across the maintainer's own apps.
**Decision.** Design the best API without preserving source-compat with v1; document every breaking change in `MIGRATION.md`.
**Rationale.** A clean break with a good guide beats contorting the design for backward-compat.
**Consequences.** Consumer apps update call sites once, guided by `MIGRATION.md`.

## ADR-003 — Target `google_mobile_ads: ^9.0.0`  ·  accepted
**Context.** v9.0.0 is current (2026-06-09); core ad flow is stable 7→9; only the adaptive-banner methods were renamed.
**Decision.** Depend on `^9.0.0`; use `getLargeAnchoredAdaptiveBannerAdSize` / `…WithOrientation`. Raise package env to Flutter ≥ 3.38.1 / Dart ≥ 3.10.0.
**Consequences.** Consumer projects must meet v9's min versions (iOS 13, Android minSdk 24 / compileSdk 36, AGP 8.13.1) and adopt the iOS `UISceneDelegate` lifecycle. Documented in `MIGRATION.md`.

## ADR-004 — Dependency injection over global singletons  ·  accepted
**Decision.** No static/singleton config; `AdFlowConfig` and collaborators are constructed and injected. A convenience accessor may exist but must be backed by an injectable instance.
**Rationale.** v1's static global forced elaborate `reset()` test plumbing and made DI impossible. Injection makes every unit independently testable.
**Consequences.** Tests construct their own graph with fakes; no shared static state to reset between tests.

## ADR-005 — One reactive primitive: ChangeNotifier / ValueListenable  ·  accepted
**Decision.** Ad state is exposed as `ValueListenable<AdLoadState>`; drop v1's hand-rolled `List<VoidCallback>` observer and its duplicate broadcast stream.
**Rationale.** Idiomatic, less code, fewer bugs, integrates with `ValueListenableBuilder`.
**Consequences.** Widgets subscribe via `ValueListenableBuilder`; one notification channel per controller.

## ADR-006 — The SDK seam is the only door to google_mobile_ads  ·  accepted
**Decision.** All plugin calls go through an `AdSdk` interface (`GmaAdSdk` real, `FakeAdSdk` for tests). Nothing else imports `google_mobile_ads` except the seam and the widgets that must host an `AdWidget`.
**Rationale.** Makes everything testable without a device, and keeps the legacy↔Next-Gen native swap invisible to our code.
**Consequences.** A little boilerplate in the seam; huge testability and future-proofing payoff.

## ADR-007 — Foreground detection via AppStateEventNotifier  ·  accepted
**Context.** v1 treated iOS `inactive` AND `paused` as backgrounding, so app-open ads fired after Control Center / permission dialogs / the app-switcher.
**Decision.** Use `AppStateEventNotifier.appStateStream` (the official signal) for foreground-return; never hand-roll off `didChangeAppLifecycleState`.
**Consequences.** Correct warm-start behavior; no false app-open triggers.

## ADR-008 — Exponential backoff + jitter for retries  ·  accepted
**Decision.** `RetryPolicy` = exponential backoff with jitter, a max attempt count, a cooldown, then **auto re-arm**. Keep v1's cancellable-`Timer` approach (not `Future.delayed`).
**Rationale.** v1's linear no-jitter backoff made managers retry in lockstep and never re-armed banner/native after cooldown.
**Consequences.** Fewer thundering-herd retries; loads recover automatically after a cooldown.

## ADR-009 — FrequencyCapPolicy: per-format + global caps  ·  accepted
**Decision.** Per-format time + count caps AND a global cross-format cap, persisted through an injected key-value store.
**Rationale.** v1 had only a per-interstitial time cooldown; nothing stopped an interstitial then an app-open back-to-back.
**Consequences.** Configurable caps in `AdFlowConfig`; a user is never hit by stacked full-screen ads.

## ADR-010 — Next-Gen SDK: opt-in, Android-only, default OFF  ·  accepted
**Context.** Next-Gen is GA on native Android but experimental in Flutter (a build-time `USE_NEXT_GEN_SDK` flag); the Dart API is unchanged. iOS has no Next-Gen.
**Decision.** Build the *capability* and document it as an experimental opt-in (`--dart-define=USE_NEXT_GEN_SDK=true`); keep legacy `play-services-ads` the default; add an example build variant that turns it on. Never enable by default; don't depend on legacy-only native internals.
**Rationale.** The revenue upside (Android) is real, the effort is low (no Dart changes), and keeping it opt-in contains the risk while it's pre-GA.
**Consequences.** README documents the flag + its Android-only, experimental status; nothing in our Dart code assumes which native SDK is active.

## ADR-011 — Manual preloading (no Flutter preload API)  ·  accepted
**Context.** The Flutter plugin has no preload API even in 9.0.0.
**Decision.** "Preload" = load ahead, cache the instance, show later; every full-screen controller reloads the next in `onAdDismissedFullScreenContent` / `onAdFailedToLoad` and keeps one warm.
**Consequences.** Higher show-rate/fill without a native preload API; respect the 4h app-open expiry.

## ADR-012 — Test ads only in code; production IDs via config  ·  accepted
**Decision.** The library never hardcodes a production ad-unit ID; consumers supply per-platform IDs via `AdFlowConfig`. A `testMode` uses Google's official sample IDs. Test-mode is derived from an explicit flag/config, NOT from resolved IDs.
**Rationale.** Prevents accidental invalid-traffic strikes and fixes v1's `isUsingTestAds` false positives.

## ADR-013 — Add rewarded interstitial with mandatory intro/skip  ·  accepted
**Decision.** Implement the missing rewarded-interstitial format, including a built-in intro/announcement screen helper with a skip option.
**Rationale.** v1 had a dead test-ID constant but no implementation; the format is policy-gated on the intro screen.

## ADR-014 — Publish as 2.0.0  ·  accepted
**Decision.** Version the rewrite `2.0.0`; maintain a clear `CHANGELOG.md`; keep the same package name, repo, and pub.dev identity.
**Consequences.** Same publishing pipeline; consumers opt in via a major bump.

## ADR-015 — v1 parked under `legacy/v1/`, excluded from analysis and publish  ·  accepted
**Context.** Phase 2 scaffolds a new `lib/` in the same paths v1 occupied, but PROGRESS requires keeping v1 greppable until its battle-tested logic (retry timing, consent-sample flow, test-mode) is ported. Leaving v1 in `lib/` would collide with the new tree and break `flutter analyze` under gma 9 lints.
**Decision.** `git mv` v1 `lib/`, `test/`, `example/` → `legacy/v1/`; exclude `legacy/**` in `analysis_options.yaml`; add `legacy/` (plus `docs/`, `.claude/`) to `.pubignore`.
**Rationale.** Satisfies both constraints: v1 stays greppable in the working tree for porting, while the package analyzes clean and publishes without it. Git history additionally preserves v1 at tag/commit `c9d95d5` (v1.3.17) / `4ecef71` (v1.3.18).
**Consequences.** Delete `legacy/` once porting is complete (Phase 13/14). `flutter test` no longer runs v1's ~1000 tests — v2 rebuilds coverage phase by phase.

## ADR-016 — Seam refinements: UMP primitives live in AdSdk; view handles build their own widget  ·  accepted
**Context.** ARCHITECTURE's sketch had `ConsentGateway` "wrapping UMP", and banner/native loads "return the plugin object because a real AdWidget must host it". Invariant 8 says only the seam imports `google_mobile_ads`.
**Decision.** (a) `AdSdk` exposes raw UMP one-call wrappers (`requestConsentInfoUpdate`, `canRequestAds`, `loadAndShowConsentFormIfRequired`, `showPrivacyOptionsForm`, statuses, `resetConsent`) as clean `Future`s; `ConsentGateway` (Phase 4) becomes pure orchestration over the seam. (b) `BannerHandle`/`NativeHandle` expose `buildWidget()` — `GmaAdSdk` returns a real `AdWidget`, `FakeAdSdk` a `SizedBox` — instead of leaking the plugin ad object.
**Rationale.** (a) keeps invariant 8 literal (one gma import) and makes ConsentGateway fully testable with `FakeAdSdk`; UMP callbacks are wrapped into Futures exactly once, per the v1 trap. (b) removes the last reason for widgets to import the plugin and lets widget tests pump real trees with fakes.
**Consequences.** `GmaAdSdk` is the single gma import in `lib/` (widgets no longer need one). Fake handles are drivable test doubles shipped in `lib/src/seam/fake_ad_sdk.dart` (whether to export them for consumers' tests is part of ADR-P3).

## ADR-017 — Hand-written immutables; no freezed/build_runner (resolves ADR-P1)  ·  accepted
**Context.** ADR-P1 proposed `freezed` to cut v1's copyWith-sentinel boilerplate.
**Decision.** Hand-write the config/state immutables; add **no** build_runner dependency. Also: **no `copyWith` until a real caller needs one** — v1's boilerplate existed to serve copyWith sentinels; the v2 configs are small consts built once at startup.
**Rationale.** A library forcing build_runner on consumers is a real cost; the config surface is ~10 small classes with no unions. Prefer deleting to adding.
**Consequences.** If copyWith becomes necessary (e.g. runtime config swaps), add it narrowly to the classes that need it, or supersede this ADR.

## ADR-018 — No `appId` field in AdFlowConfig  ·  accepted
**Context.** ARCHITECTURE's sketch had `required this.appId` "(or null → set in manifest/plist)".
**Decision.** Drop the field. The AdMob application ID cannot be set at runtime by the Flutter plugin — it is read from `AndroidManifest.xml` (`com.google.android.gms.ads.APPLICATION_ID`) and `Info.plist` (`GADApplicationIdentifier`) only.
**Rationale.** A config field the SDK never reads is a lie that would burn integration time.
**Consequences.** README/MIGRATION document the manifest/plist requirement prominently. `AdFlowConfig` carries ad *unit* IDs only.

## ADR-019 — ATT handled by UMP; no `app_tracking_transparency` dependency  ·  accepted
**Context.** v1 depended on `app_tracking_transparency` and sequenced the ATT prompt itself. RESEARCH §5: UMP can present the ATT explainer and the system prompt (IDFA message configured in the AdMob console), and double-prompting must be avoided.
**Decision.** v2 has no direct ATT dependency. `UmpConsentGateway` lets UMP drive ATT; the README documents: configure the IDFA message in AdMob's Privacy & messaging, add `NSUserTrackingUsageDescription` to `Info.plist`, and do NOT also call `app_tracking_transparency` yourself.
**Rationale.** One consent surface, one prompt sequence, one less dependency; matches Google's current guidance.
**Consequences.** Apps wanting a custom pre-ATT explainer outside UMP must implement it themselves before `AdFlow.initialize`. Timeout design: only the info-update step has a timeout (30s default) — the form step never times out because the user may legitimately keep it open.

## ADR-020 — Consent flow degrades to `canRequestAds()` on failure, surfacing `lastError`  ·  accepted
**Context.** v1 swallowed consent errors with `catchError((_){})` (weakness #12); Google's sample continues after "consent gathering failed" because a previously-consented (or not-required) user should still get ads offline.
**Decision.** `ensureCanRequestAds()` never throws: update/form failures and timeouts are captured as a typed `AdFlowError` on `ConsentGateway.lastError`, and the method returns the SDK's own `canRequestAds()` answer. Concurrent calls join the in-flight run (double-load guard).
**Consequences.** Callers branch on the bool; diagnostics read `lastError`. `showPrivacyOptions()` DOES rethrow — a user-initiated surface should show its failure.

## ADR-021 — Interstitial user-action pacing activates on first `recordUserAction()`  ·  accepted
**Context.** AdMob guidance: ≤ 1 interstitial per 2 user actions. But enforcing `minActionsBetween` (default 2) unconditionally would silently block every interstitial in apps that never call `recordUserAction()` — a trap for integrators.
**Decision.** Action pacing is dormant until the app's first `recordUserAction()` call. Untracked apps are paced by frequency caps alone; once the app reports actions, `show()` requires `minActionsBetween` actions since the last show (counter resets on show).
**Rationale.** Opt-in enforcement can't brick monetization by omission, yet gives policy-conscious apps the exact guardrail.
**Consequences.** README must tell integrators to call `recordUserAction()` at natural breaks to get action pacing.

## ADR-022 — Public surface: zero google_mobile_ads re-exports; FakeAdSdk ships via `ad_flow_testing.dart` (resolves ADR-P3)  ·  accepted
**Context.** ADR-P3 proposed a minimal curated re-export of plugin types. As built, the seam's own value types (`FixedBannerSize`, `AdPaidEvent`, `RewardEarned`, `MaxContentRating`, …) cover the entire public API — no plugin type leaks through any signature.
**Decision.** The main barrel re-exports **nothing** from `google_mobile_ads`. Consumers needing plugin internals (mediation extras, custom `AdRequest`s) import the plugin directly. Test doubles (`FakeAdSdk`, fake handles) ship in a separate `package:ad_flow/ad_flow_testing.dart` barrel so consumers can unit-test their integration; `InMemoryKeyValueStore` is already public via the policy exports.
**Rationale.** Re-exporting plugin types couples consumers to plugin majors for no gain; a clean seam plus an explicit escape hatch is strictly simpler. Shipping the fakes makes downstream apps testable the same way ad_flow itself is.
**Consequences.** MIGRATION documents "import google_mobile_ads directly if you need more" (table row already present). Fake knobs become semi-public API — additive changes only.

## ADR-023 — Rewarded interstitial intro presenter is injected at `AdFlow.initialize`  ·  accepted
**Context.** The intro screen needs a `BuildContext` at show time; the facade has none.
**Decision.** `AdFlow.initialize` takes a `rewardedIntroPresenter` (e.g. `(content) => RewardedIntroScreen.show(navigatorKey.currentContext!, content)`) and **fails fast with `invalidConfig`** when the rewarded interstitial slot is configured without one.
**Rationale.** Failing at init is discoverable; failing at first show in production is not. Injection keeps the controller free of navigation concerns and testable.
**Consequences.** README shows the navigatorKey pattern. Apps with custom intro UIs pass their own presenter (must keep a skip path — policy).

## ADR-024 — Concurrency-safety pass: synchronous re-entry guards close three real races  ·  accepted
**Context.** A Phase-14 adversarial review (partially completed before hitting a spend limit — 3 of 5 finder dimensions ran, verifiers mostly failed) produced unverified findings; three were independently reproduced with hand-written repro tests and confirmed real:
1. **Double-load**: `load()` checked `_state.value` synchronously but only wrote `AdLoading` *after* `await _gate.canLoad(...)`. Two concurrent `load()` calls both passed the check, both hit the SDK, and the second call's handle silently overwrote `_handle`, leaking the first (undisposed).
2. **Double-show**: same pattern in `show()` — `_state.value = AdShowing` was written *after* `await _gate.canShow(...)`. Two concurrent `show()` calls on one controller both passed the `AdLoaded` check and both called `handle.show()` on the same single-use handle (repro: `showCalls == 2`).
3. **Cross-controller coordinator race**: `FullScreenAdCoordinator.enter()` was called only from the `AdShowedEvent` handler, i.e. after `handle.show()` resolves. Two *independent* controllers sharing one coordinator (e.g. `InterstitialAdController` + `AppOpenAdController`) each ran `AdGate.canShow`'s `if (coordinator.isFullScreenAdVisible) return false;` check — an `async` function — and since neither had entered yet, both read `false` in the same synchronous turn and both proceeded to show (repro: `bothShown == true`).
A fourth reproduced issue was a design gap, not a race: a `BannerAdController` whose one load attempt landed while the gate was closed (ads disabled / consent not yet open) dropped to `AdIdle` with no timer scheduled — nothing ever tried again, even after the gate reopened (repro: banner stayed at 1 handle forever until the fix; recovered to normal refresh cadence after).
**Decision.**
- `load()` in `FullScreenAdControllerBase`, `BannerAdController`, `NativeAdController`: write `_state.value = AdLoading` **synchronously**, before the `await _gate.canLoad(...)` call, rolling back to `AdIdle` if the gate rejects. A concurrent `load()` call now sees `AdLoading` immediately and bails — no yield point exists between the check and the write.
- `FullScreenAdCoordinator` gained `tryEnter()`: an atomic, synchronous check-and-claim (`if (isFullScreenAdVisible) return false; enter(); return true;`). `FullScreenAdControllerBase.show()` now calls `_coordinator.tryEnter()` as its first action (before any `await`), sets `AdShowing` in the same synchronous turn, and — critically — **bypasses `AdGate.canShow`'s own (still-racy) coordinator check**, calling `_gate.canLoad(slot)` + `_caps.canShow(slot)` directly instead for the remaining consent/cap checks, rolling both the coordinator claim and the state back to `AdLoaded` if either rejects. `AdGate.canShow` itself is unchanged and remains valid for external/read-only "would a show succeed" queries — it is simply no longer in the *decision* path of `show()`.
- `BannerAdController`/`NativeAdController`/`FullScreenAdControllerBase` gained `_scheduleGateRecheck()`: when `canLoad` rejects a load, reuse the existing single `_timer` field to retry after `_retry.cooldown`, exactly like the existing retry-after-failure re-arm (ADR-008) but triggered by a gate rejection instead of an SDK error.
**Rationale.** In Dart's single-threaded event loop, a synchronous check-then-write is atomic with respect to any other `async` call, because nothing else can run until the current synchronous stack unwinds to an `await`. Every one of these three races existed because the guard state was written *after* an `await`, leaving a window. The coordinator fix in particular could not be solved by moving `enter()` earlier inside `show()` alone (tried first, still raced) — it required a **synchronous** primitive on the coordinator itself, since the race was between two different controller instances, not two calls on one controller.
**Consequences.** `AdGate.canShow`'s documented contract (checks coordinator + canLoad + caps) is now accurate only for callers other than the full-screen controllers themselves; note this if adding a new full-screen-adjacent caller. All three races and the banner-recovery gap have permanent regression tests (`full_screen_ad_coordinator_test.dart` `tryEnter` group, `interstitial_ad_controller_test.dart` `concurrency safety` group, `cross_controller_coordinator_test.dart`, `banner_ad_controller_test.dart` `gate-blocked recovery` group).

## ADR-025 — Sequential invariant self-review (1,2,5,6,8,9) closes Phase 14, finds and fixes a real staleness bug  ·  accepted
**Context.** ADR-024 fixed the 3 races the spend-limited review had reproduced, but that review only completed 3 of 5 planned dimensions and never adversarially verified invariants 1, 2, 5, 6, 8, 9. Per the maintainer: "mostly verified is not good enough" for a monetization SDK. Did a focused, sequential (no parallel subagents — that's what hit the spend limit), manual pass: state each invariant, cite the enforcing code, check every path (including the ADR-024 class of "check → await → act" race, seam bypasses, static state, hardcoded ids), write a failing repro first for any hole, fix, confirm green; add or confirm a regression test either way.
**Findings, invariant by invariant:**
- **Invariant 1 (consent gates every load).** Solid: every `_sdk.load*` call in every controller is preceded by `await _gate.canLoad(slot)`, and after ADR-024 the write race is closed too. Gap found: `RewardedAdController`, `RewardedInterstitialAdController`, `AppOpenAdController` had no per-format "no load while consent closed" test (only the shared base's interstitial test covered the mechanism) — added one to each of their test files.
- **Invariant 2 (privacy options entry point) — REAL BUG FOUND AND FIXED.** `PrivacyOptionsButton` read `ConsentGateway.isPrivacyOptionsRequired` as a plain `bool` getter inside a `StatelessWidget.build()`. A widget built before the first `ensureCanRequestAds()` resolves (or mounted across a later re-check) never rebuilds when the requirement later flips true — it stays permanently hidden, violating "a persistent control MUST be available." Wrote a failing test first (confirmed the staleness both directions), then fixed: `ConsentGateway` gained `ValueListenable<bool> get privacyOptionsRequired` (backed by a `ValueNotifier`, updated everywhere `_refreshPrivacyRequirement()` runs) and a `dispose()` method; `PrivacyOptionsButton` now wraps its body in `ValueListenableBuilder`. `AdFlow` tracks whether it created its own `ConsentGateway` (`_ownsConsent`) and only disposes a self-created one, never an injected one.
- **Invariant 5 (rewarded interstitial intro+skip first).** Solid, and structurally enforced, not just by convention: `_handle` is declared in `full_screen_ad_controller_base.dart` and Dart's underscore privacy is per-FILE, so `RewardedInterstitialAdController` (a different file) cannot reach it directly — the only way to reach `handle.show()` is `super.show()`, which the subclass's override always gates behind the intro. Added a missing dispose-mid-intro regression test (confirmed already safe, no fix needed).
- **Invariant 6 (no hardcoded production ad-unit IDs).** Solid: grepped `lib/` and `example/` for `ca-app-pub` — every hit is either a doc-comment placeholder or Google's sample publisher id (`3940256099942544`). The testMode-with-a-platform-gap scenario (slot configured for Android only, testMode on, iOS still resolves to the Google sample id rather than null) was already covered by an existing test.
- **Invariant 8 (SDK seam is the only door to the plugin).** Solid: exactly one file (`lib/src/seam/gma_ad_sdk.dart`) imports `google_mobile_ads`. Turned this into a permanent executable check: `test/architecture/seam_boundary_test.dart` greps `lib/` for plugin imports outside the seam and fails if any exist (verified it actually catches a violation before relying on it).
- **Invariant 9 (no global mutable state).** Solid: the only mutable `static` in `lib/` is the sanctioned `AdFlow._instance` (ADR-004's injectable-backed convenience pointer), correctly set only after a fully-constructed instance and cleared via `identical()` on dispose. Added `test/architecture/no_global_state_test.dart`, a permanent grep-based check allow-listing only that one line (verified it catches a violation too).
**Closed the two incomplete review dimensions:**
- **seam-api**: re-verified `GmaAdSdk`'s mappings not yet spot-checked against the pub-cache 9.0.0 source — confirmed `AppOpenAd` genuinely has no `setServerSideOptions` (unlike `RewardedAd`/`RewardedInterstitialAd`), confirmed `NativeAd.customOptions` type, `AdWidget`/`FullScreenContentCallback` generics, and the rewarded `show()` `required` callback is always satisfied even when the seam's own `onUserEarnedReward` is null. No new bugs found.
- **test-gaps**: closed two gaps directly created by ADR-024/this ADR's own fixes — `AdFlow.dispose()` idempotency, and `_ownsConsent`-based disposal (self-created gateway's `ValueNotifier` becomes provably unusable post-dispose; an injected one provably survives) — plus a banner-in-unbounded-width confirming test (behavior was already correct: no load attempted, no crash, just a permanent placeholder, since an adaptive banner cannot be sized without a real width).
**Rationale.** A monetization SDK's compliance invariants are exactly the kind of thing that "looks solid" but silently breaks (invariant 2's bug required a specific mount-timing pattern — a persistent settings tab mounted at app start — that none of the existing tests happened to exercise). Sequential, single-threaded self-review with the ADR-024 race-pattern specifically in mind is what caught it; a broader adversarial fleet is valuable but not a substitute for someone actually reading the invariant text against the code.
**Consequences.** `ConsentGateway` is now a slightly larger interface (`privacyOptionsRequired` + `dispose()`); the only implementation is `UmpConsentGateway`, updated. Two new architecture tests (`test/architecture/`) act as regression guards for invariants 8 and 9 specifically, independent of any future code review. 205 tests green (up from 186 at end of Phase 13).

## ADR-026 — Independent code review (Opus, commit `3ede24d`): 1 blocker + 3 majors + 4 minors + 2 test-hardening items + nits, all fixed  ·  accepted
**Context.** A second independent review (static reading, four passes, every finding hand-verified against source — `docs/ad_flow_v2/REVIEW_FINDINGS.md`) found four must-fix defects that cluster exactly where ADR-025 predicted unit tests can't see: the live plugin seam and controller timing. Fixed in commit order, each with a failing-test-first repro; items 11-13 are lower-severity test-hardening/nit fixes from the same review, handled last per the review's own ordering.
1. **BLOCKER — a rejected `handle.show()` wedged every full-screen format for the rest of the session.** `FullScreenAdControllerBase.show()` claimed the coordinator and set `AdShowing` synchronously, then `await handle.show(...)` with no `try`/`catch`. The documented `AdSdk.show` contract says failures arrive via `AdFailedToShowEvent`, never a rejected Future — but a real implementation can violate that (ad released between load and show, channel error, mediation failure), and when it did, the exception unwound past `_exitCoordinator()`/`_dropHandle()`, leaving the coordinator claimed forever (every format shares one `FullScreenAdCoordinator`). Fix: wrap the dispatch; on catch, exit the coordinator, drop the handle, route through `AdFailed` + immediate reload — the same recovery path already used for `AdFailedToShowEvent`. `FakeFullScreenAdHandle` gained `showRejectsWith` to reproduce this without touching the real plugin.
2. **MAJOR — banner auto-refresh crashed every ~60s.** `BannerAdListener.onAdLoaded` fires on every AdMob-driven refresh of a `BannerAd`, not just the first load, but `GmaAdSdk._finishBannerLoad` called `completer.complete(handle)` unconditionally — the second firing threw `Bad state: Future already completed` as an unhandled async error. This bug lives entirely inside `GmaAdSdk`'s plugin wiring, which `FakeAdSdk` cannot model (it's one-shot, not a persistent listener) — reproducing it required real platform-channel testing, which started the seam test suite (below). Fix: guard the completion with `if (!completer.isCompleted)`, still refreshing the handle's size/collapsible fields on every firing.
3. **MAJOR — a stale retry timer stomped a since-recovered `AdLoaded`/`AdShowing` state, leaking a handle and a subscription.** `_scheduleRetry`'s timer callbacks unconditionally reset to `AdIdle` and reloaded, with no check that the controller was still `AdFailed`. If a load failed (arming a timer) and the controller separately recovered before that timer fired — a `show()`-triggered `load()` succeeding, or a direct `load()`/`reload()` call — the stale timer still fired, stomping the recovered state and starting an unrelated second load that overwrote `_handle`/`_contentSub` with no dispose of the original. Fixed in `FullScreenAdControllerBase` and `NativeAdController` (both cited) by guarding every retry callback with `if (_disposed || _state.value is! AdFailed) return;`. Also checked `BannerAdController`'s identical `_scheduleRetry` shape (not cited by name, same code) and applied the same guard for consistency — though banner's own successful-load path *always* calls `_scheduleRefresh()`, which cancels+replaces the one shared `_timer` field outright, so this specific race isn't actually reachable there; the guard is defensive, not a reproduced fix, and the banner test documents that distinction rather than claiming a false repro.
4. **MAJOR — `NativeAdController.reload()` reopened the ADR-024 double-load race.** `reload()` reset state to `AdIdle` unconditionally, even while a `load()` was already in flight (state `AdLoading`, suspended mid-SDK-call) — defeating `load()`'s own synchronous re-entry guard and letting two concurrent `loadNative` calls race, the second silently overwriting `_handle` with no dispose. Fix: `reload()` is now a no-op while `AdLoading` — the in-flight load already owns the slot and will resolve on its own. Also hardened `FullScreenAdControllerBase.discardCurrentAd()` with the identical guard per the review's precaution; its one current caller (`AppOpenAdController.show()`) only invokes it after confirming `isReady` (implies `AdLoaded`), so this isn't reachable through today's call graph, but it's `@protected` and a future subclass could call it differently.
5. **The real `GmaAdSdk` seam (~660 LOC) had zero tests** — every prior "N tests prove correctness" claim rested on "`FakeAdSdk` faithfully models the plugin," unverified. Established `test/seam/gma_ad_sdk_test.dart`, driving the actual plugin via `TestWidgetsFlutterBinding` + a mock method-channel handler for `instanceManager.channel` (pattern mirrors the plugin's own `test/ad_containers_test.dart`/`test/banner_ad_test.dart`, reachable in the pub cache under `~/.pub-cache/hosted/pub.dev/google_mobile_ads-9.0.0/test/` but not importable across packages — the ~15-line `sendAdEvent`/mock-handler setup is reproduced locally). Covers: banner load + the finding-#2 refresh crash; interstitial load-success, exactly-one-dismiss-event, `onAdFailedToLoad` → `AdFlowError` mapping through the real `AdMessageCodec`, and a rejected `show()` (confirms finding #1's premise was a real plugin failure mode, not hypothetical); `appForegroundEvents`' first subscription triggering `startListening` on the separate app-state channel.
6. **`FakeAdSdk` was more forgiving than the real SDK.** A second `show()` never failed and impossible event orderings (dismiss before show, reward after dismiss) were silently accepted — a controller bug reaching either state wouldn't have been caught. Hardened `FakeFullScreenAdHandle`: a second `show()` now emits `AdFailedToShowEvent` (matching the real single-use SDK) instead of repeating; `simulateDismissed()` before any `show()` throws `StateError`; `simulateReward()` after `simulateDismissed()` throws. Ran the full suite after each change — no existing test relied on the old over-permissive behavior.
7. **MINOR (child-directed/test-device apps: effectively MAJOR) — `updateRequestConfiguration` was gated on the consent result at init.** It sends no ad request (pure config), so gating it was unnecessary and harmful: if consent resolved *later* than init (a delayed privacy-options grant, a first-launch form that failed), controllers loading ads from that point on never got `testDeviceIds`/`tagForChildDirectedTreatment`/`maxAdContentRating`/`tagForUnderAgeOfConsent` applied — a registered test device would get live ads (self-click/invalid-traffic risk); a child-directed app would serve untagged/wrongly-rated ads (COPPA/policy risk). Fix: `_start` now runs `sdk.updateRequestConfiguration(...)` unconditionally, in the same `Future.wait` as init/consent, independent of the gate result. ARCHITECTURE.md's init sequence corrected to match.
8. **MINOR (design) — `AdGate.canShow` re-embodied the exact ADR-024 coordinator race and had no caller** — kept (public API), not deleted; its doc now warns explicitly and points to `FullScreenAdCoordinator.tryEnter()`; a test proves the race concretely (two sequential `canShow()` calls both return `true` in the same turn).
9. **MINOR (design) — an app-open ad could fire immediately behind another format's dismiss.** On dismiss, the coordinator clears synchronously, before the app's own warm-start signal necessarily settles — so only an app-configurable (and possibly zero) `globalFrequencyCap.minGap` stood between an interstitial closing and an app-open opening, unlike invariant 4's explicit "never immediately after another ad closes." Fix: `FullScreenAdCoordinator` gained a `lastExitAt` timestamp (harmless — recorded on every `exit()`, doesn't affect `tryEnter()`/`isFullScreenAdVisible`/`visible` at all, so no other controller's tests changed); `AppOpenAdManager` gained an optional `coordinator` + `postDismissSuppression` (default 1s) and skips showing — but still warms the next ad — while within that window since the coordinator's last exit, regardless of which format caused it. `AdFlow` now wires its shared `_coordinator` into the manager. One pre-existing test asserted the OLD (buggy) immediate-show behavior as correct; updated it to advance past the suppression window, and added a dedicated test for the suppression itself plus a contrast test showing no suppression applies when no coordinator is wired (documenting why the facade always passes one).
10. **MINOR — adaptive banners reserved a flat 50dp placeholder, causing residual layout shift on wider layouts.** Researched Google's actual documented bounds (web search, since RESEARCH.md didn't cover this and the formula isn't in the plugin's Dart source — it varies by device on the native side): anchored adaptive banner height is 50–90dp, capped at 15% of device height, with **no pure-width formula** — so no more-precise client-side calculation is possible without a platform round trip. `BannerAdController.reservedHeight` keeps the 50dp floor (now documented as a floor, not an estimate) and gained a `kind` getter; `AdFlowBanner` computes its own device-aware placeholder for adaptive kinds — `(MediaQuery.sizeOf(context).height * 0.15).clamp(50, 90)` — deliberately biased toward the upper end of Google's documented range, since an under-reservation (real ad taller than reserved space, pushing content down) is the direction "Layout Encourages Accidental Clicks" enforcement targets; an over-reservation only wastes some whitespace. `placeholderHeight` remains the fully-precise override when the real height is known in advance; both the dartdoc and README now say so explicitly. One pre-existing test asserted the old flat-50 placeholder; updated it, and added a dedicated test verifying the floor/mid-range/ceiling of the formula against three viewport heights.
11. **TEST HARDENING — `no_global_state_test`'s regex under-enforced invariant 9.** The `static final <UpperCamelCase-type>` exemption (added so `TestAdUnitIds`' fields wouldn't false-positive) was too broad — it would just as happily wave through `static final ValueNotifier<int> _shared = ValueNotifier(0);`, the shape invariant 9 actually guards against. Tightened to exempt only `static const`, the one construct Dart itself guarantees is immutable; no legitimate `static final` exists in `lib/` today, so this costs nothing.
12. **TEST HARDENING — invariant 6 (no hardcoded production ad-unit IDs) had no dedicated architecture-fitness test.** `ad_flow_config_test.dart` proved test-mode *behavior* is correct but nothing scanned `lib/` for a stray literal ID elsewhere in the tree. Added `test/architecture/no_hardcoded_ad_ids_test.dart`, mirroring `seam_boundary_test.dart`'s grep-the-source-tree pattern: every `ca-app-pub-<publisher>` match in `lib/` must carry Google's sample publisher id (`3940256099942544`).
13. **NIT — banner/native seam handles leaked their `StreamController`s on load failure.** `GmaAdSdk.loadBanner`/`loadNative`'s `onAdFailedToLoad` callbacks disposed the underlying `BannerAd`/`NativeAd` but never closed the handle's `_events`/`_paid` controllers — harmless in practice (the handle is discarded with nothing left listening) but inconsistent with the success path's disposal discipline. Added `unawaited(handle._events.close())`/`unawaited(handle._paid.close())` to both. No dedicated regression test: `_Gma*Handle` fields are private to `gma_ad_sdk.dart` (Dart's per-file, not per-class, privacy), so nothing outside that file can observe controller-closed state — a test would need to duplicate the seam's internals to check it, which isn't worth doing for a leak with no observable effect.
**Rationale.** Same as ADR-025: these bugs cluster exactly where unit tests structurally can't reach (live plugin wiring, timer/async races) — a second independent review looking specifically at those seams found four more real defects the first pass's invariant-by-invariant read didn't surface, because none of them are invariant violations per se; they're implementation races and a missing test layer.
**Consequences.** `test/seam/gma_ad_sdk_test.dart` is now the canonical place to add coverage for any new `GmaAdSdk` behavior — extend it rather than trusting `FakeAdSdk` alone for anything touching the plugin's actual callback/completer wiring. `FakeFullScreenAdHandle`'s stricter behavior is a (minor) breaking change for any external test code built on `ad_flow_testing.dart` that happened to call `show()` twice or drive events out of order — acceptable since `ad_flow_testing.dart` is new and pre-1.0-of-the-testing-surface.

## ADR-027 — `AdFlow._start()` bounds `sdk.initialize()` with a 30s timeout (example-app hang triage)  ·  accepted
**Context.** Asked to diagnose a reported problem running `example/` after the v9 upgrade. Reproduced on the Android emulator (`flutter run -d emulator-5554 -v`, full trace captured): the app never got past its native launch splash. `adb`/`dumpsys` confirmed a genuine indefinite hang, not slowness — the app process sat at 0% CPU for 5.5 minutes straight, `dumpsys activity activities` showed the native `Splash Screen` window still topmost the whole time, no ANR was ever raised, no exception was ever logged. Traced via logcat to the last line the app process ever emitted: `DynamitePackage: Instantiating com.google.android.gms.ads.ChimeraMobileAdsSettingManagerCreatorImpl` — Google Play Services' own Chimera/Dynamite module loader for `com.google.android.gms.ads.dynamite`, which fires automatically at Android process start (visible in logcat before "Flutter run key commands," i.e. before Flutter's engine has even connected), independent of when or whether Dart code calls `MobileAds.instance.initialize()`. The emulator in question had 0 Google accounts signed in (`adb shell dumpsys account`) — a known trigger for Play Services' Dynamite-module bootstrap to hang instead of failing fast on emulators without a warmed-up/signed-in Play Store.
**Investigated and ruled out** (checked against the exact suspects the upgrade could plausibly have introduced, per RESEARCH.md §1, before concluding it was environmental): Android build — `com.android.application 8.11.1`, `minSdk`/`compileSdk` via `flutter.*Version` — built and installed cleanly, no Gradle/AGP error, app launched and ran up to the native hang. iOS — `Podfile`'s `platform :ios, '13.0'` line is commented out, but `Runner.xcodeproj`'s `IPHONEOS_DEPLOYMENT_TARGET` is already `13.0` on all three configs; `pod install` (after fixing an unrelated local shell-locale crash — `LANG`/`LC_ALL` unset — nothing to do with this repo) auto-assigned `iOS 13.0` and `flutter build ios --no-codesign` succeeded with zero errors (only pre-existing deprecation warnings from the plugin's own Objective-C, not ours). macOS target — fails immediately with "No macOS desktop project configured" (the example was never `flutter create --platforms=macos`'d); not investigated further since `google_mobile_ads` doesn't support desktop at all (RESEARCH.md §1) and this isn't upgrade-related.
**Decision.** The emulator-specific native freeze itself is **not fixable in `ad_flow`'s code** — it happens before Flutter's Dart isolate runs at all, so no Dart-level change (including a timeout) can observe or route around it; it is a Play-Services/device-state issue, reproducible with any AdMob-using app on the same emulator, not something the v9 upgrade or `ad_flow` introduced. Confirmed this by re-running with the fix below already applied — the emulator hung identically, at the identical log line, proving the freeze predates any Dart code executing.
However, while tracing the hang, found a **real, fixable gap it exposed**: `AdFlow._start()`'s `Future.wait([_sdk.initialize().catchError((Object _) {}), ...])` had no timeout on the init call, unlike `UmpConsentGateway`'s existing (and consciously reasoned) `infoUpdateTimeout`. RESEARCH.md documents the native SDK's init call as completing "on init or a 30s timeout," but that is the native SDK's own promise, not `ad_flow`'s to rely on — the emulator repro proved that promise can fail to hold (5.5 minutes, no completion). Since `AdFlow.initialize()` is `Future.wait`-gated and the example app (following `ad_flow`'s own documented pattern) gates its entire home screen on that Future via `FutureBuilder`, a native SDK that is merely *slow* rather than *permanently frozen* — a real, non-hypothetical case on a cold network, a first-run Play Services warmup, a restrictive corporate MDM — would previously wedge the whole app's UI forever with zero error surfaced. Fixed with a private `_initTimeout = Duration(seconds: 30)` constant wrapping `_sdk.initialize()` via `.timeout()`, mirroring `ConsentGateway`'s pattern exactly; on timeout it's swallowed by the existing `catchError` (loads already retry independently of init success). `updateRequestConfiguration` and the consent form step were deliberately left unguarded — the former wasn't implicated in the repro and is a lightweight config setter, not the expensive Dynamite-bootstrap path; the latter's existing "no timeout, a user may keep the form open for minutes" comment is correct by design and must not change.
Reproduced with a failing test first: added `FakeAdSdk.initializeHold` (a `Completer<void>?`, mirroring the existing `consentUpdateHold` knob) so `initialize()` can be made to hang without touching the real plugin; a `fakeAsync`-driven test in `ad_flow_test.dart` proves `AdFlow.initialize()` used to never resolve when the SDK's `initialize()` hangs (confirmed the failure before fixing), and now resolves within the 30s timeout.
**Rationale.** A timeout that can't be verified against every possible native failure mode is still worth adding when (a) the failure mode is real and reproducible at the boundary this code actually controls (the Dart-level `Future`, not the native call inside it), and (b) the blast radius of *not* having it is "the entire app never renders its home screen, with no error, no matter how long the user waits" — the worst possible failure mode for a wrapper library whose one job is to never be the reason the host app breaks.
**Consequences.** `AdFlow._start()` now degrades gracefully (ads simply don't load, same as any other init failure) instead of hanging forever if `sdk.initialize()` doesn't return within 30s. This is implementation-only — no public API changed. `FakeAdSdk.initializeHold` is a new (additive) testing-surface knob. The emulator-level freeze itself remains unaddressed by this change (see Context) — if the user hit that same freeze, the fix here will not resolve it; the recommended remediation is signing into a Google account on the AVD, using a fresh/cold-booted "Google Play"-image AVD, or testing on iOS/a physical device instead.

**Addendum — round 2, same freeze re-reported, no code change.** The freeze recurred on a later run, at the identical `ChimeraMobileAdsSettingManagerCreatorImpl` log line, this time with the screen stuck on the *native* Flutter splash rather than the Dart `CircularProgressIndicator` — meaning the round-1 fix's 30s timeout never got a chance to run its `.catchError`. Diagnosed with temporary `debugPrint`s bracketing every step of `_start()` and `UmpConsentGateway._run()` (all reverted after diagnosis — no trace of them survives). Only the first `begin` print ever fired for each; nothing else, ever, across 20+ minutes. To distinguish "one slow `Future`" from "the isolate itself is stuck," queried the Dart VM service directly over HTTP (`getIsolate?isolateId=...`) — that request **also timed out** (5s, no response). A `.timeout(Duration)` is serviced by the same isolate's timer queue as everything else; if the isolate can't answer a VM-service safepoint query, it can't run its own timeout timer either. Conclusion: the native Ads-Dynamite bootstrap isn't merely slow-but-eventually-async (the case ADR-027 fixes) — it blocks Android's platform/UI thread synchronously, and that stalls the whole Dart isolate with it, timers included. No Dart-level timeout, on `initialize()` or anywhere else, can route around a synchronously-blocked platform thread. This is a hard limit of what a Flutter *wrapper library* can defend against — the fix has to happen at the native SDK/plugin layer or the device/emulator's Play-Services state, never in `ad_flow`'s Dart code. Re-confirmed via `git diff` (empty after reverting the diagnostic prints) and `flutter analyze` (clean) that no code change resulted from this round — the correct action was ruling it out, not patching around it.

**Addendum — round 3, fresh emulator after a full host restart, same freeze, stronger evidence, no code change.** User restarted their computer, deleted the emulator entirely, and created a brand-new one (different device profile — Pixel 10 Pro, "Google Play" image, not "Google APIs"). The freeze reproduced at the identical `ChimeraMobileAdsSettingManagerCreatorImpl` log line — ruling out stale local AVD state as the cause (round 1/2's remediation suggestions assumed a corrupt/never-signed-in AVD; this round shows a genuinely fresh one fails identically). Confirmed real network reachability first (`dumpsys connectivity` showed both WiFi and cellular transports `EVER_VALIDATED&IS_VALIDATED`), ruling out "the emulator has no internet" as the cause. Re-added temporary diagnostics — this time a `Timer.periodic(Duration(seconds: 3))` heartbeat in `ExampleApp` itself (independent of `AdFlow` entirely) plus prints in `build()`/`FutureBuilder`/`_start` (all reverted after diagnosis, confirmed via empty `git diff` on `example/lib/main.dart`) — and let it run to completion instead of stopping early. Findings: `build()` ran, `_start` began, `FutureBuilder` reached `ConnectionState.waiting` (the first frame *did* get built) — but the heartbeat **never fired once**, not even after the Dynamite bootstrap line. At `+252182ms` (~4m12s), `flutter run` itself printed `Service protocol connection closed.` / `Lost connection to device.` and exited cleanly (code 0) — the Dart VM Service connection died outright, not merely stopped responding to one query as in round 2. This is stronger than round 2's evidence: it's not "the isolate stopped answering," it's "the engine connection was torn down." Cross-referenced the exact log signature (`Instantiating com.google.android.gms.ads.ChimeraMobileAdsSettingManagerCreatorImpl` immediately followed by total silence) against public reports: [googleads/googleads-mobile-flutter#429](https://github.com/googleads/googleads-mobile-flutter/issues/429) documents the identical signature from an unrelated developer in 2022, on both real devices and emulators.

**⚠️ CORRECTED by ADR-028 — the "unfixable / environmental" conclusion of this ADR and all three addenda was WRONG.** The freeze *was* an `ad_flow` bug, introduced by this same review pass (finding #5), and it *is* fixed in Dart. All three rounds above reached the right *mechanism* (a synchronous platform-thread block during the native Ads-Dynamite bootstrap stalls the whole isolate, which is why no Dart timeout fired) but the wrong *cause* — they assumed the block was intrinsic to the native SDK/device rather than triggered by `ad_flow`'s own call ordering. The tell that should have redirected the investigation sooner: the freeze only ever appeared *after* review-fix #5 moved `updateRequestConfiguration` into the concurrent `Future.wait`, and the user's very first bug report explicitly flagged #5 as the prime suspect. The missing step in rounds 1–3 was reading the *plugin's* native source to see which method calls run on the platform thread vs. a background thread — done in round 4 (ADR-028), which found and fixed it. Keeping this ADR and its addenda intact (not deleting them) as an honest record of a multi-round misdiagnosis: the discipline that eventually worked was reading the collaborator's source instead of concluding "not our layer," per SKILL.md §5.

## ADR-028 — the example-app freeze was ours after all: `updateRequestConfiguration` must run AFTER `initialize()`, never concurrently  ·  accepted (supersedes ADR-027's "unfixable" conclusion)
**Context.** Re-opened the ADR-027 freeze on a fourth run (fresh Pixel 10 Pro / Google Play emulator, new host session) with the discipline the first three rounds skipped: **read the `google_mobile_ads` plugin's own Android source** to see how each seam call is dispatched natively, rather than treating everything below the Dart seam as an opaque "native SDK / environment" box.
**Root cause (verified against `~/.pub-cache/hosted/pub.dev/google_mobile_ads-9.0.0/android/`):** the two native calls `AdFlow._start()` was firing concurrently are dispatched on *different threads*, and they race the same singleton:
- `MobileAds#initialize` → `FlutterMobileAdsWrapper.initialize()` runs `MobileAds.initialize(context, listener)` inside **`new Thread(...)`** — a background thread. It never blocks the platform thread.
- `MobileAds#updateRequestConfiguration` → handled **synchronously inside `GoogleMobileAdsPlugin.onMethodCall` on the platform (UI) thread**, and `FlutterRequestConfiguration.updateRequestConfiguration()` calls both `MobileAds.getRequestConfiguration()` *and* `MobileAds.setRequestConfiguration()`.

Those `MobileAds.get/setRequestConfiguration()` calls force the native Ads (Play Services Dynamite) settings-manager singleton — `ChimeraMobileAdsSettingManagerCreatorImpl`, the exact class named in the last log line before every freeze — to bootstrap **on the platform thread**, at the same moment `initialize()`'s background thread is bootstrapping the very same singleton. On a cold device (first launch, module not yet cached) the two threads race to instantiate/lock that singleton and **deadlock the platform thread**. Because the Flutter engine drives the Dart isolate's event loop *from* the platform thread, a wedged platform thread freezes the entire isolate — no first frame rasterizes, no `Timer` fires, no `.timeout()` resolves, and eventually the VM-service connection itself dies. Every symptom rounds 1–3 documented, now with a cause.

This is squarely a regression from **review-fix #5**: before #5, `updateRequestConfiguration` was gated behind consent, so in practice it ran *after* `initialize()` had already bootstrapped the module on its background thread — the race never happened. #5 correctly identified that gating config on the consent *result* was wrong (test-device/COPPA settings could be skipped), but its fix — running config *concurrently* with init via `Future.wait` — introduced the deadlock. The two concerns are separable: config must be **unconditional** (not gated on consent) **and** **ordered after init** (not concurrent with it).
**Decision.** `AdFlow._start()` now: kicks off consent (independent, parallel-safe); `await`s `_sdk.initialize()` (bounded by the existing `_initTimeout`); *then* `await`s `_sdk.updateRequestConfiguration(...)`; then `await`s consent before starting loads. Config is still applied unconditionally regardless of the consent *result* (preserving #5), just no longer racing init. On a healthy device init completes in well under a second, so the added ordering is invisible; on the frozen emulator it is the difference between a fully-rendered home screen with all six formats loading and a permanent hang.
**Verified by running (per SKILL.md — the step that was missing for three rounds):** applied the fix, `flutter run` on the same Pixel 10 Pro emulator that had frozen four times → the app rendered the full HomeScreen, every full-screen format reached `ready`, the native ad rendered ("AdMob native ad validator: No implementation issues found"), and the anchored banner showed the live "Test Ad — This is a 468x60 test ad." No freeze. Regression-tested first: a `fakeAsync` test in `ad_flow_test.dart` holds `FakeAdSdk.initializeHold` open and asserts `updateRequestConfiguration` is **not** called until `initialize()` completes — confirmed it fails against the old concurrent `Future.wait` (config recorded while init pending) and passes against the ordered code. 230 tests green, `flutter analyze` clean.
**Consequences.** Implementation-only; no public API change. The fix generalizes beyond the emulator: any first-launch cold start where the Dynamite module isn't cached (a real user's first run, a cleared-data reinstall) was at risk of the same platform-thread race, not just this test host — so this closes a genuine production hang, not merely an emulator annoyance. ADR-027's `_initTimeout` stays (belt-and-suspenders for a genuinely slow-but-async init) but is no longer load-bearing for this failure mode. New RESEARCH.md §3 / SKILL.md §6 trap recorded: **never call `MobileAds.updateRequestConfiguration` before `initialize()` completes** — the plugin services it synchronously on the platform thread and it will race init's background bootstrap of the ads settings-manager singleton. The broader lesson (SKILL.md §5): when a hang looks like it's "below our layer," read the collaborator's actual source to confirm *which thread* each call runs on before concluding it's unfixable — three rounds of black-box diagnosis reached the right mechanism but the wrong, defeatist cause.

## ADR-029 — never build banner/native controllers inside `build()`; harden the widgets against a controller swap  ·  accepted
**Context.** Full interactive on-emulator test of the example (all six formats driven via `adb`) after the ADR-028 fix. Every format worked, but the **native ad and the bottom banner went blank the moment a reward was earned** — and stayed blank. The control case that isolated it: showing an *interstitial* (a full-screen activity transition with **no** `setState`) left both ads rendered, whereas showing a *rewarded* ad (same transition, but its reward callback calls `setState` to bump the coin counter) blanked them. So the trigger was `setState`, not the activity transition — ruling out an Impeller/platform-view-resume theory.
**Root cause.** The example built its ad controllers *inside* `build()`: `AdFlowNativeAd(controller: ads.native())` and `AdFlowBanner(controller: ads.banner())`. Each `ads.native()`/`ads.banner()` call mints a **fresh** controller and kicks off a **new** ad load. So every `setState` (the coin update) handed both widgets brand-new, unloaded controllers. `AdFlowNativeAd` only called `controller.load()` in `initState` — which does not re-run when the parent rebuilds with a new controller (the `State` is reused) — so the swapped-in controller never loaded: a permanent blank, plus the old controller leaked (still loading, never disposed). Two faults: a **misuse in the example** (the documented contract is "one controller per placement", created once) and a **missing safety net in the widgets** (no `didUpdateWidget`, so a swapped controller silently dead-ended).
**Decision.** Fix both:
1. **Example** (`example/lib/main.dart`): hoist the banner/native controllers to `late final` `State` fields, created once, never in `build()`. This is the idiomatic pattern and the one the README/dartdoc already imply.
2. **Widgets** (`AdFlowNativeAd`, `AdFlowBanner`): add `didUpdateWidget` — on an `!identical` controller, dispose the old one (when `ownsController`) and load/re-arm the new one. Turns a silent permanent-blank-and-leak into correct (if wasteful) behavior, so the footgun can't brick a consumer's UI. Purely additive; a stable controller (the correct usage) hits the `identical` fast-path and is unaffected.
**Verified by running:** rebuilt on the same emulator; earned rewards through **two** `setState` cycles (coins 0→10→20) — native + banner stayed rendered both times (they blanked before the fix). All six formats confirmed working interactively end-to-end: interstitial (shows after the 2-action pacing gate, dismisses, reloads), rewarded (shows, grants coins, reloads), rewarded-interstitial (mandatory intro+skip screen first, shows, grants, reloads), native + banner (render, survive `setState`, banner auto-refreshes), app-open (shows on warm return). Two new `didUpdateWidget` regression tests (native + banner) fail against the un-hardened widgets and pass against the fix; 232 tests green, analyze clean.
**Observation (not changed):** app-open shows on the *second* background→foreground cycle, not the first — the first foreground event is consumed as the cold-start suppression (`AppStateEventNotifier` doesn't replay the cold-launch foreground because `GmaAdSdk.appForegroundEvents` calls `startListening()` lazily, after the app is already foregrounded — see the SKILL.md §6 trap). This errs toward *not* showing app-open (the policy-safe direction — invariant 3), so it's left as-is; "fixing" it risks showing app-open on a genuine cold start.

## ADR-030 — client-driven ATT + presenter-based consent/ATT explainers (restores v1's `initializeWithExplainer`)  ·  accepted (amends ADR-019)
**Context.** v1 shipped `AdFlow.instance.initializeWithExplainer(context:, consentTexts:, attTexts:)` — pre-consent and pre-ATT priming screens the maintainer uses in every app — but it coupled the package to `BuildContext` and sequenced ATT itself via `app_tracking_transparency`. ADR-019 dropped that dependency for v2, letting UMP drive ATT (IDFA message configured in the AdMob console), because one consent surface / one prompt sequence is simpler. That is still the right **default**, but the maintainer wants the v1 priming flow back — client-controlled copy, client-controlled ATT ordering — as an **option**, redesigned for v2 (see `docs/ad_flow_v2/EXPLAINER_V2_SPEC.md`).
**Decision.** Add an **opt-in, additive** priming layer; the default (pass nothing) is byte-for-byte today's UMP-driven behaviour, so this is not a breaking change.
- **Presenter pattern, not `BuildContext`.** Two typedefs mirror `RewardedIntroPresenter`: `ConsentExplainerPresenter` / `AttExplainerPresenter` (both `Future<void> Function(Content)`). The app supplies the UI (typically via a `navigatorKey`), so the package never holds a `BuildContext`. Ready-made `ConsentExplainerScreen` / `AttExplainerScreen` (+ `ConsentExplainerContent` / `AttExplainerContent` copy classes, `const`, localizable, with `copyWith` — the narrow copyWith ADR-017 explicitly sanctions) copy the `RewardedIntroScreen` shape.
- **Client-driven ATT re-added behind the seam (amends ADR-019).** `AdSdk` gains `AttStatus` + `getTrackingAuthorizationStatus()` / `requestTrackingAuthorization()`; `GmaAdSdk` implements them via the re-added `app_tracking_transparency` dependency (iOS only via `defaultTargetPlatform`; non-iOS → `notSupported`, no channel call). This dependency is used **only** when an `attExplainer` is supplied. ADR-019's "no ATT dependency, UMP drives it" remains the default path; this ADR narrows ADR-019 from "never" to "not unless the app opts into client-driven ATT."
- **Order (matches v1): ATT first, then GDPR.** `UmpConsentGateway._run`: if `attExplainer != null` and status is `notDetermined` → app's ATT primer → `attPromptDelay` (200 ms, Apple's guidance) → system prompt; then the unchanged consent info update; then the GDPR form — **primed only when a form will actually appear** (`getConsentStatus() == required && isConsentFormAvailable()`, a v2 improvement over v1's blanket `showExplainer` bool). **⚠️ The original design here also let `skipGdprConsentIfAttDenied` skip the GDPR *form* itself when ATT was denied — a GDPR-compliance bug, corrected by ADR-031: the required form is now ALWAYS shown and the (renamed) flag `skipConsentPrimerIfAttDenied` gates only the optional primer.**
- **A broken primer never blocks consent.** A throwing presenter is caught, recorded on `lastError`, and the real system prompt / form still runs. Every existing gateway guard is preserved (info-update timeout, degrade-to-`canRequestAds()`, in-flight join, `lastError`).
- **Facade wiring.** `AdFlow.initialize` gains `consentExplainer`, `attExplainer`, `consentExplainerContent`, `attExplainerContent`, `skipConsentPrimerIfAttDenied` (renamed by ADR-031), threaded into a self-created `UmpConsentGateway` (an injected gateway is used verbatim — construct it with these yourself). `_start`'s init/consent parallelism is unchanged; the explainer simply extends the consent future.
**Rationale.** The maintainer relies on the priming flow for install-time opt-in rates; losing it in v2 was a real regression. The presenter pattern removes v1's only architectural sin (the `BuildContext` coupling) while keeping the package testable with `FakeAdSdk` (a settable `attStatus`, a configurable `requestTrackingAuthorization` result + call counter — the whole flow is unit-tested with no device). Making it opt-in preserves ADR-019's "one prompt by default" simplicity for apps that want it.
**Consequences.** `app_tracking_transparency` is a dependency again (README/MIGRATION "dependency removed / drop it" notes corrected: it is now re-added but exercised only in client-driven mode). Apps enabling client-driven ATT must NOT also configure the UMP IDFA message in the AdMob console, or the user sees two prompts — documented in the README, MIGRATION, the facade dartdoc, and the example's inline comment. The public surface grows by two screens, two content classes, two typedefs, one enum, and two seam methods — all additive. `ConsentGateway`'s interface is unchanged (the explainer knobs are `UmpConsentGateway` constructor params, not interface methods). New SKILL.md §6 trap: an explainer presenter must be context-safe; the package never holds a `BuildContext`.

## ADR-031 — ATT denial must never suppress a REQUIRED GDPR form (compliance fix + rename)  ·  accepted (corrects ADR-030)
**Context.** ADR-030 ported v1's `skipGdprConsentIfAttDenied` (default true): when the user was prompted for ATT and denied it, the entire step-3 GDPR block — including `loadAndShowConsentFormIfRequired()` — was skipped. An adversarial self-audit reproduced the consequence with a failing test: an **EEA** user (UMP reports consent `required`, a form available) who denies ATT never sees the GDPR consent form (`loadAndShowConsentFormCalls == 0`). That is a real compliance defect. **ATT (Apple, device-level tracking authorization) and GDPR (EU, personal-data processing consent) are independent legal regimes.** Denying ATT does not satisfy — and must not suppress — a required GDPR consent form. v1 conflated them; "matching v1" carried the bug forward.
**Decision.**
- `UmpConsentGateway._run` now **always** calls `loadAndShowConsentFormIfRequired()` (it no-ops natively when no form is required, and shows the required form otherwise). This line is the compliance guarantee and is never gated on ATT.
- The flag is **renamed** `skipGdprConsentIfAttDenied` → `skipConsentPrimerIfAttDenied` and its scope narrowed: it now suppresses only the optional consent **primer** (the soft priming screen), never the form. Renamed rather than kept because a parameter literally named `skipGdprConsentIfAttDenied` that is documented to *not* skip GDPR consent is a latent trap for the next reader — exactly the class of bug this audit exists to remove. The rename is safe: unpublished (`2.0.0-dev.1`), no external call site, and the example uses the default.
- Default stays `true` (skip the primer for a just-denied user — a harmless UX optimization); `false` shows the primer too. Either way the required form shows.
**Rationale.** The one job of a consent layer is to not silently drop a legally-required consent surface. An optimization flag that can override that is never acceptable; the flag is kept (per the maintainer) but constrained to something it cannot get wrong.
**Consequences.** Compliance guaranteed by a regression test (`consent_gateway_test.dart` → the `skipConsentPrimerIfAttDenied (COMPLIANCE…)` group: EEA + ATT denied → `loadAndShowConsentFormCalls == 1`, primer skipped). Behaviour change vs ADR-030 for exactly one path (EEA + fresh ATT-deny): the GDPR form now appears where it previously didn't. `README`/`MIGRATION` updated; `EXPLAINER_V2_SPEC.md` §3/§5's "skip step 3 form" / "ATT denied → consent form NOT shown" lines are superseded by this ADR (annotated inline). No new global state; the seam-boundary test was also extended to guard `app_tracking_transparency` (previously only `google_mobile_ads`), verified to catch a violation.

## ADR-032 — non-blocking `AdFlow.initialize()`: return immediately, run startup in the background  ·  accepted
**Context.** `initialize()` built the whole graph synchronously but then `await`ed `_start()` — which gathers UMP consent (a network round-trip, sometimes a user-interactive form) and the Ads SDK init — before returning. The example (and any app following the documented `FutureBuilder<AdFlow>` pattern) therefore gated its first frame on that Future, so on weak/blocked internet the user stared at a splash until consent resolved: **exactly v1's pain** that v2 set out to remove. Audit finding.
**Decision.** Make `initialize()` non-blocking:
- Build the graph synchronously (it always was), set the `_instance` pointer synchronously, kick `_start()` in the **background** (via `_begin()`, storing the future), and **return immediately** — before consent.
- Add `Future<bool> get whenReady` (backed by that stored future) that completes when the consent gate resolves (value = `canRequestAds()`), for the rare caller that must await it. Errors are captured (`_start` degrades internally; `_begin` adds a `.catchError(=> false)` last-resort net) so a background failure never becomes an unhandled async error or a throwing `whenReady`. **Not required for normal use.**
- `_start()` now returns the gate result and, since it runs in the background, checks `_disposed` after awaiting consent — a caller can `dispose()` mid-startup, and we must not start the app-open manager or kick preloads on a torn-down graph.
- **Kept the `Future<AdFlow>` return type** (the Future simply completes on the next microtask now) rather than switching to a synchronous `AdFlow`. Chosen for low churn AND correctness: `initialize` stays `async`, so a *synchronous* constructor failure (a missing `rewardedIntroPresenter`) still surfaces as a **rejected Future** (preserving the fail-fast test); and every existing `await AdFlow.initialize(...)` call site keeps compiling. A synchronous `AdFlow` return would have tripped the `await_only_futures` lint at ~15 `await AdFlow.initialize(...)` sites and turned the fail-fast throw synchronous — more churn for no real gain, since the honest signal ("construction is instant") is delivered by the Future resolving before consent, documented in MIGRATION.
- Example drops the `FutureBuilder<AdFlow>` gate: `main()` awaits `initialize()` (resolves instantly — construction only) and `runApp`s `HomeScreen` directly; consent/ATT/explainer screens push over the already-visible app via the `navigatorKey`.
**Rationale.** A wrapper library's one job is to never be the reason the host app's UI stalls. Graph construction is synchronous and cheap; only consent/init are slow, and neither needs to block rendering because every `load()` already gates on `canRequestAds()` (invariant 1) — so ads simply appear when the gate opens, over a UI that was interactive from frame one.
**Consequences.** Behavior change (documented): the `initialize` Future now resolves before consent rather than after. Two prior tests that asserted "after `await initialize`, consent has resolved / config applied / `initialize` is still pending while init hangs" were refocused onto `whenReady` (the ADR-027 30s init timeout now bounds the **background** startup / `whenReady`, not `initialize`; the ADR-028 init→config ordering is preserved **inside** the background `_start` for the internal preloads — but an adversarial review found it did NOT hold for *on-demand* first-frame banner/native/manual loads, which bypass `_start`; that config-before-load hole is closed by **ADR-033**). Invariant 1 is unchanged and re-guarded (`NON-BLOCKING …` and `whenReady completes false … nothing loads` tests assert no load happens before the gate opens; a widget test proves the tree renders while consent is still pending). New SKILL.md §6 trap. `whenReady` is additive public API.

## ADR-033 — config-before-load gate: no ad request before `updateRequestConfiguration`, even for on-demand first-frame loads (closes an ADR-032 regression)  ·  accepted
**Context.** An adversarial multi-agent review of ADR-032 (7 confirmed findings) surfaced a real compliance regression the non-blocking change introduced. Before ADR-032, `initialize()` returned only after `_start` finished (init → **config** → consent → preloads), so the instance — and therefore any on-demand `ads.banner()`/`ads.native()`/`controller.load()` — was unreachable until request configuration had been applied. ADR-032 publishes the instance and returns immediately, and the example now mounts a banner/native on the **first frame**. Those on-demand loads gate only on `AdGate.canLoad` = `isEnabled() && canRequestAds()` — a **consent** check, independent of `MobileAds.initialize()`/`updateRequestConfiguration()`. On a cold device where the Dynamite bootstrap is slow (the ADR-027/028 scenario), a non-EEA/returning user's `canRequestAds()` flips true (UMP info-update is fast) while `_start` is still parked on `await _sdk.initialize()` — so a first-frame banner/native load fires **before** `updateRequestConfiguration`. Result: the first ad request goes out without `testDeviceIds` (a registered test device gets a live ad → invalid-traffic risk) or without `tagForChildDirectedTreatment`/`maxAdContentRating` (a child-directed app sends an untagged/wrongly-rated request → COPPA/policy violation). This is exactly the defect review-fix #5 / ADR-028 exist to prevent; ADR-032 preserved the ordering only for `_start`'s internal preloads (kicked after the config await), not for app-driven loads. Reproduced with a failing test (banner load recorded while `initializeHold` held config back).
**Decision.** Add a **config-readiness gate**. `AdFlow` holds a `Completer<void> _configApplied`, completed in `_start` immediately after `updateRequestConfiguration` (and in `dispose()`, so a mid-startup teardown doesn't leave a load parked). `AdGate.canLoad` now `await`s `configReady` before the consent check, so **every** load path (preload OR on-demand) waits until request configuration is applied — the first frame still renders instantly (only the ad *request* waits, and it is bounded by the existing 30s init timeout, so it never hangs). `configReady` is an optional `AdGate` param (default: an already-complete future) so isolated policy/controller tests are unaffected.
**Rationale.** The config-before-load ordering is a distinct requirement from the consent gate; `canRequestAds()` never enforced it, and only `initialize`'s old blocking return had been (accidentally) doing so. Making the gate itself await config makes the guarantee structural and independent of startup timing.
**Consequences.** No public API change (`AdGate.configReady` is internal; the facade wires it). Regression test: an on-demand banner mounted immediately after `initialize()` with the gate open but init held records no `loadBanner` until `requestConfigs` is populated. README §3 / MIGRATION §2 "safe to render at once" is now *accurate* (loads wait for config **and** consent), not merely aspirational. Same review also added the two missing tests ADR-032 lacked — the `_disposed`-during-startup guard (discriminated via a new `FakeAdSdk.hasForegroundListener`, since controllers self-guard so a naive assertion is non-discriminating) and the `whenReady` error-capture net (a throwing `canRequestAds()` → `_start` rejects → `whenReady` resolves `false` without throwing) — plus promoted the non-blocking contract into `initialize`'s and the class `///` dartdoc (it had lived only in a `//` body comment). SKILL.md §6 trap added.

**Addendum — `_configApplied` must ALWAYS complete (config-gate robustness).** A follow-up audit found the initial ADR-033 fix released the config gate only on the normal path: a *hanging* `updateRequestConfiguration` (it had no timeout, unlike init) left `_configApplied` incomplete forever, so every load — now awaiting it in `AdGate.canLoad` — would hang forever (worst on weak internet). Fixed: `_start` bounds the config call with `.timeout(_initTimeout)` (covers a hang) and wraps init+config in a `try/finally` that completes `_configApplied` no matter what (covers any throw, e.g. a synchronous `toRequestConfig()`). Loads now DEGRADE (proceed without config) rather than hang on a startup hiccup. Fail-first test: a held config → a first-frame banner never loads (old code); after the timeout it proceeds (fixed). Plus a throwing-config regression test.

## ADR-034 — errors DEGRADE, never wedge: every boundary catches `Object`, not just `AdFlowError`  ·  accepted
**Context.** The `AdSdk` seam's contract says it throws `AdFlowError`. A real platform channel does not honour contracts: `MissingPluginException`, `PlatformException` and plain `StateError`s all reach us from the plugin (and from `shared_preferences`) in the wild. Every layer that must degrade was catching `on AdFlowError` only. The 2026-07 audit found three live consequences: (a) a throwing `FrequencyCapPolicy`/gate inside `FullScreenAdControllerBase.show()` — reached AFTER the coordinator was claimed and `AdShowing` written — escaped with the coordinator still claimed, permanently blocking EVERY full-screen format for the session; (b) a raw throw from any `load*` escaped `load()` and pinned the slot at `AdLoading`, which `load()`'s own re-entry guard then rejects forever, with no retry armed; (c) a raw throw from the ATT seam aborted the WHOLE consent flow — no info update, no GDPR form, no privacy-options entry point, zero ads.
**Decision.** Every catch on a degradation path catches `Object` and normalizes through a new `asAdFlowError(error, fallbackKind)`. `show()`'s post-claim preconditions run inside a `try` that rolls back the coordinator claim and the state on ANY throw. ATT is isolated in its own `try` so it can never abort the GDPR flow (the *crash* counterpart to ADR-031's *policy* rule). `recordImpression` on the show path is `catchError`-guarded so a throwing store cannot raise an unhandled async error.
**Rationale.** Losing one impression is always better than wedging a format — or the whole app's ad layer — for the rest of the session. The failure modes here are silent and permanent, which is the worst possible shape.
**Consequences.** Unexpected error types now surface as `AdFailed` / `ConsentGateway.lastError` instead of escaping. Guarded by `test/controllers/error_containment_test.dart` and `test/consent/consent_resilience_test.dart`.

## ADR-035 — the consent flow is RETRIED, and the gate WAITS for it (weak-network revenue)  ·  accepted (amends ADR-032/033)
**Context.** Two independent holes, both invisible in production because a closed gate looks exactly like a user who declined, and both worst on this package's actual user population (mostly weak/slow/intermittent networks).
1. The consent flow ran **exactly once per session**. A launch in airplane mode — or on a connection too slow for the 30s info-update timeout — left UMP with no determination, `canRequestAds()` false, and nothing to ever re-ask. The result was **zero ads for the entire session**, even when the network returned seconds later. Gate re-checks re-ran `load()`, never consent.
2. ADR-032 made startup non-blocking, so the app renders and mounts banner/native on the first frame. But the ADR-033 config gate (SDK init, ~1s, no user interaction) always opens well BEFORE consent (network-bound info update, plus possibly an ATT prompt and a GDPR form a human must read). So the first-frame view load read a still-false `canRequestAds()`, failed fast, and re-armed only after `RetryConfig.cooldown` — **5 minutes** — with nothing to nudge it when consent opened moments later. Every new install therefore showed blank banner and native slots through the first five minutes of its first session: the highest-value window, on every app.
**Decision.** `AdGate.canLoad` gains a `settleConsent` callback (alongside ADR-033's `configReady`), wired to `AdFlow._settleConsent`, which (a) joins the in-flight consent attempt rather than reading a not-yet-true answer, and (b) RE-ATTEMPTS a consent flow that previously **failed**, rate-limited to one UMP call per 10s. A user who merely **declined** is a settled answer, not a failure (`lastError == null`) and is never re-run — re-prompting them on a timer would be hostile and a policy problem. Separately, `_scheduleGateRecheck` now uses a new `RetryPolicy.gateRecheckDelay` (exponential from `baseDelay`, capped at `maxDelay`) instead of the failure `cooldown`: a closed gate is a "not yet", not an error.
**Rationale.** The two fixes are the same insight — the consent gate is not a one-shot fact, it is a *process*, and both the loader and the gate must treat it as one.
**Consequences.** BEHAVIOUR CHANGE: a consent form can now appear later in a session (when a failed flow is retried after the network returns) rather than never. A permanently closed gate (Remove-Ads, declined consent) settles into a cheap once-a-minute check. Guarded by `test/facade/weak_network_recovery_test.dart` (verified failing against the old behaviour).

## ADR-036 — adaptive banners follow the layout width (reload on rotation/fold)  ·  accepted
**Context.** An anchored/inline adaptive banner is requested FOR a specific width. `AdFlowBanner` latched `_loadRequested` on the first finite layout and never re-requested, and `BannerAdController` cached the stale `_width` — so after a rotation the ad was letterboxed in the slot AND every subsequent 60s refresh re-requested that same wrong size, for the rest of the session. Google's own guidance is to reload an adaptive banner when the orientation changes.
**Decision.** `BannerAdController.resize(width)` + `loadedWidth`; `AdFlowBanner` drives `resize` from its `LayoutBuilder`, guarded on an **actual** width change.
**Rationale.** The guard is the load-bearing part: re-requesting on every rebuild would be an ad-request storm (invalid traffic). A width change is a real, infrequent, physical event; a rebuild is not. A rotation mid-load is reconciled after the in-flight request lands, so rapid rotation coalesces instead of firing a request per frame.
**Consequences.** Fixed-size banners ignore width entirely (their size is not width-derived). Guarded by three tests in `test/widgets/ad_flow_banner_test.dart`.

## ADR-037 — a broken device clock must not permanently block every ad  ·  accepted
**Context.** `StoredFrequencyCapPolicy` persists impression timestamps. If the device clock is AHEAD when an ad shows (a cheap handset with a dead RTC before NTP lands — common on weak networks; or a user who set the clock forward to skip an in-app cooldown), the stored timestamp is in the future. `now - last` is then negative, which is always `< minGap`, so that slot — and, via the global cap, EVERY full-screen format — was blocked **forever**, across restarts, with no recovery short of clearing app data.
**Decision.** Both read paths ignore future-dated timestamps, and `_push` prunes them, so the bad value self-heals on the next impression.
**Rationale.** A timestamp in the future is garbage, not a recent impression. Treating it as "0 seconds ago" is the worst possible reading.
**Consequences.** No weakening of normal capping (guarded by a test). Found by the completeness critic in the 2026-07 audit.

## ADR-038 — package-supplied screens must scroll, because their dismiss control is mandatory  ·  accepted
**Context.** The rewarded-interstitial intro and both consent/ATT primers were unscrollable centred `Column`s. On a small device at a large accessibility text scale they overflowed and pushed their LAST child off-screen, where it is also not hit-testable. Measured at 320x568 / 200% scale with the package's own default copy: 128px overflow (rewarded intro), 704px (ATT primer), 1536px (consent primer). The rewarded intro's last child is the **AdMob-mandated skip option** — so this rendered a required opt-out unreachable, which is a policy violation, not a UX nit. The primers became un-escapable dead ends in front of the GDPR form. Localized copy is routinely longer than English, so this was reachable well below 200% for many users.
**Decision.** A shared internal `ExplainerBody` centres content when it fits and scrolls when it does not. All three screens use it.
**Consequences.** Any NEW package-supplied screen must use `ExplainerBody` (or scroll some other way). Guarded by `test/widgets/text_scale_overflow_test.dart`.

## ADR-039 — the GLOBAL frequency cap gates INVOLUNTARY ads only  ·  accepted
**Context.** `globalFrequencyCap` (shipped default: `minGap: 15s`) was applied to every full-screen format. So a user who tapped **"watch an ad for 100 coins"** ten seconds after an interstitial happened to fire got **no ad, no reward and no explanation** — the highest-eCPM format in the package, silently refused by a cap meant for something else entirely.
**Decision.** The global cap was doing two jobs. Its real one is pacing **involuntary** ads — an interstitial or app-open the user never asked for. It must not block a **user-initiated** one. `StoredFrequencyCapPolicy` gains `globalCapExemptSlots`; `AdFlow` exempts the rewarded and rewarded-interstitial slots (the latter is reached only by tapping "continue" on the mandatory intro, so it too is user-initiated). Their impressions are **still recorded** globally, so an involuntary interstitial still cannot fire straight after one. `RewardedConfig` / `RewardedInterstitialConfig` gain their own `cap` (unlimited by default) for publishers who do want a per-format limit.
**Rationale.** The exemption belongs on the *block*, not on the *record*. Capping a rewarded ad means refusing a user who explicitly asked for one — a UX and revenue loss with no policy upside.
**Consequences.** DEFAULT/BEHAVIOUR CHANGE. Guarded by `test/controllers/cap_semantics_test.dart`.

## ADR-040 — the frequency gap runs from the previous ad's DISMISS, not its SHOW  ·  accepted
**Context.** `recordImpression` fired on `AdShowedEvent`, so every cap timestamp was stamped when the ad **appeared**. The gap then ran down *while the user was still watching*: a 30s rewarded ad under a 15s global gap used the whole gap up on screen, so an interstitial could fire **the instant the user closed it** — two full-screen ads back to back, the exact thing the global cap exists to prevent.
**Decision.** Record the impression on `AdDismissedEvent`. A safety net records it on `dispose()` / `AdFailedToShowEvent` too, if the ad reached the screen but its dismiss never arrived, so the cap cannot under-count.
**Rationale.** "One ad every N seconds" means N seconds of *app*, not N seconds that an ad is allowed to consume.
**Consequences.** BEHAVIOUR CHANGE. Counts (`maxPerHour`/`maxPerSession`) now land at dismiss too, which keeps them consistent with the gap. Guarded by `test/controllers/cap_semantics_test.dart`.

## ADR-041 — client-side banner refresh OFF by default; a refresh never blanks the slot  ·  accepted
**Context.** Two problems in one timer. (a) `BannerConfig.minRefresh` defaulted to 60s, but **AdMob already auto-refreshes banner ad units server-side**, configured per ad unit in the console and **on by default**. The client timer was therefore a second, unsynchronised refresh loop on the same placement: up to 2x the ad requests, for no extra revenue. (b) When it fired it **dropped the live handle, went `AdIdle` and started a fresh load** — so the slot went BLANK for the whole duration of that load, every cycle (multi-second on a weak network), and a refresh that merely *failed* (no-fill — routine) left it empty until a retry finally succeeded, having destroyed a perfectly good ad to get there.
**Decision.** `minRefresh` is now `Duration?`, default **null = no client-side refresh, no timer**. When a publisher does opt in, the replacement is loaded in the **background** and swapped in only on success; the old handle is disposed *after* the swap. A **failed** refresh keeps the current ad on screen and backs off. A **gate-closed** refresh (Remove-Ads, consent withdrawn) still drops the ad — that is not a failure; the ad is simply no longer permitted.
**Rationale.** Refresh rate is an AdMob-console concern. And an ad already on screen is worth more than the one that might replace it.
**Consequences.** DEFAULT + BEHAVIOUR CHANGE. The swap is `AdLoaded → AdLoaded`, and `ValueNotifier` skips `notifyListeners()` on an equal value, so `BannerAdController` gains a `revision` `ValueListenable` that bumps on every handle swap; `AdFlowBanner` listens to **both**. Without it the widget would go on rendering the old, disposed handle. Guarded by `test/controllers/banner_refresh_test.dart`.

## ADR-042 — an app-open ad never stacks on a banner/native ad  ·  accepted
**Context.** Two distinct holes. (a) A **click** on a banner opens the landing page and backgrounds the app; when the user returns, `AppStateEventNotifier` reports an ordinary foreground event, so the manager handed them an app-open ad *the moment they closed the first ad*. (b) AdMob objects to an app-open ad covering content that is itself already showing an ad — but nothing above the seam knew a banner was on screen.
**Decision.** (a) The banner/native controllers report `opened`/`clicked` to the shared `FullScreenAdCoordinator` (`noteViewAdOpened`); the manager consumes that **latch** on the next foreground event. A latch, **not** a time window: the user may spend seconds or minutes on the landing page, so no timeout can tell "back from the ad" apart from "back from elsewhere". Exactly one foreground event is suppressed. (b) New `AdFlow.setBlockingViewAdVisible(bool)` lets the app declare that a blocking banner/native ad occupies the screen.
**Rationale.** (b) is deliberately app-driven: whether a given banner is "blocking" is a question about the app's own layout (a small anchored banner under the content usually is not; a full-bleed native card is). ad_flow cannot know it, so it must not guess. Placement remains partly the integrator's responsibility, and the docs say so.
**Consequences.** BEHAVIOUR CHANGE + new public API. `BannerAdController`/`NativeAdController` take an optional `coordinator` (the facade passes it). Guarded by `test/lifecycle/app_open_placement_test.dart`.

## ADR-043 — app-open shows on the FIRST genuine warm return  ·  accepted (supersedes the cold-start latch)
**Context.** `AppOpenAdManager` swallowed its first foreground event as "the cold start". But the platform **never emits one**: `GmaAdSdk.appForegroundEvents` calls `AppStateEventNotifier.startListening()` lazily, *after* the app is already foregrounded, so the cold-launch foreground is never delivered. The latch was therefore eating a **real** background→return — one lost app-open impression in **every session**, on both platforms. (SKILL §6 recorded this as intended-and-safe; it was wrong, and the ADR-030-era reasoning behind it was factually wrong for both platforms.)
**Decision.** Remove the latch. Every foreground return may show an ad, including the first.
**Rationale.** Invariant 3 ("never show on a cold launch") does not need the latch — it holds **structurally**: at cold launch no ad is loaded yet, so `show()` finds nothing warm and returns false. That is now covered by its own test, so the invariant is guarded by a property of the system rather than by a counter.
**Consequences.** BEHAVIOUR CHANGE. `AppOpenConfig.showOnColdStart` is `@Deprecated` and **ignored**: it could never do what its name promised (no cold-launch event exists to act on), and its only real effect — un-suppressing the first warm return — is now the default. Guarded by `test/lifecycle/app_open_placement_test.dart`.

## ADR-044 — `AdFlow.initialize()` is idempotent  ·  accepted
**Context.** Apps re-initialize: on login/logout, on a config change, on a debug hot restart. Every call built a **whole new graph** and simply overwrote the `_instance` pointer — leaving the previous one fully alive: still subscribed to the foreground stream, still preloading and refreshing, still able to show ads, and coordinating through its **own** `FullScreenAdCoordinator`, so it could not even see the new graph's ads. Two app-open reactors on one stream, each blind to the other: **v1 trap #6, back in through the front door.**
**Decision.** `initialize()` disposes the previous instance — **after** constructing the new graph, so a throwing constructor (e.g. a missing `rewardedIntroPresenter`) leaves the working graph intact rather than tearing it down for nothing.
**Consequences.** `dispose()` on a superseded instance stays a safe no-op and does not clear the pointer to the live one. Multiple *simultaneous* `AdFlow` graphs are explicitly not supported. Guarded by `test/facade/reinitialize_test.dart` — the decisive assertion is that no foreground listener survives disposing the second graph.

## ADR-045 — `AdBlockReason`: a diagnostic surface, NOT a new `AdLoadState` case  ·  accepted
**Context.** A refused load left the controller at `AdIdle` — which is also exactly what "nothing has been requested yet" looks like. Consent never gathered, Remove-Ads still on, and a frequency cap quietly doing its job were **indistinguishable**, and the package logs nothing (`avoid_print` is on). "Why aren't my ads showing?" was unanswerable from inside the app.
**Decision.** New `enum AdBlockReason`; `AdGate.loadBlockReason()` (with `canLoad()` collapsing it to a bool); `controller.lastBlockReason` on every controller; one `AdFlow.onAdBlocked = (slot, reason) {}` callback for the whole graph.
**Rationale.** Deliberately **not** a new `AdLoadState` case. `AdLoadState` is `sealed`, so adding one would break every exhaustive `switch` in every consuming app — a breaking change, and unacceptable in a minor release. A parallel diagnostic channel gets the same information out with zero breakage.
**Consequences.** Purely additive. Most reasons are NORMAL (a cap working; a user skipping the rewarded intro), so this is a diagnostic channel, not an error channel — documented as such. Guarded by `test/facade/diagnostics_test.dart`.

## ADR-046 — banner refresh/resize interleavings: defer, re-validate, reconcile  ·  accepted
**Context.** 2026-07 production-hardening audit (multi-agent, adversarially verified; all three findings confirmed with independent fakeAsync repros). ADR-041's background refresh runs with state still `AdLoaded`, guarded only by the private `_refreshing` flag — which `resize()` never consulted. A rotation during an in-flight refresh: (1) started a concurrent load whose completion overwrote `_handle`/subscriptions without disposing what the refresh had installed — a leaked live `BannerAd` per occurrence; (2) the refresh continuation never re-checked state/width after its await, so it could destroy a fresher right-width ad, install a stale one and record the stale width; (3) the refresh's catch cancelled a retry/gate-recheck timer the load path owned and replaced it with a callback that no-ops outside `AdLoaded` — a permanently blank slot with no re-arm.
**Decision.** `resize()` defers while `_refreshing` (width recorded; the refresh reconciles). The refresh continuation bails (disposing its fresh handle) unless still `AdLoaded`, and after a swap reconciles `_width != requestWidth` exactly like `load()` does. The catch path backs off only while a current ad exists.
**Consequences.** Guarded by the `refresh/resize interleaving` group in `banner_refresh_test.dart` and by the seeded fuzz suite (ADR-054). The general lesson joins SKILL §6: every continuation that installs a resource after an await must re-validate that the world it captured still exists.

## ADR-047 — a handle swap must REMOUNT the plugin's AdWidget (ObjectKey per handle)  ·  accepted
**Context.** The plugin's `AdWidget` has no `didUpdateWidget`: its platform view captures the ad id at creation, and Flutter recreates a platform view only when its `viewType` changes (never — one constant per plugin). ADR-041's swap rebuilt the subtree with the NEW handle, but the framework updated the old element in place — the screen kept hosting the platform view of the just-DISPOSED ad. After the first refresh swap the slot was permanently dead on a real device while the controller kept requesting, installing and disposing fresh ads it never displayed. The in-place update also inverted the plugin's mount bookkeeping (its dispose unmounts the NEW ad's id, never the old one's).
**Decision.** `AdFlowBanner`/`AdFlowNativeAd` wrap the hosted subtree in `KeyedSubtree(key: ObjectKey(handle))` — a swap unmounts/mounts, running the plugin's initState/dispose bookkeeping against the right ids.
**Consequences.** Platform-view identity is unobservable in widget tests; the tests pin the keyed-remount mechanism, and the fix should be sanity-checked on-device with `minRefresh` set. Trap recorded in SKILL §6.

## ADR-048 — seam hardening: refresh survival, dispatch normalization, reactive dimensions  ·  accepted
**Context/Decision.** Three seam fixes. (a) `_finishBannerLoad`'s inline-adaptive failure branch ran its teardown unconditionally — on an AdMob auto-refresh whose `getPlatformAdSize` failed it destroyed the LIVE mounted banner and closed its streams (the exact mirror of review finding #2); now a refresh keeps the last known size and only the initial load fails. (b) The load DISPATCH itself (`ad.load()` / the static full-screen `load`s) can reject with a raw `PlatformException` the callback mapping never sees; it is now wrapped — cleanup + `asAdFlowError` — upholding the seam's documented contract. (c) `BannerHandle.dimensions` (`ValueListenable<AdDimensions>`): a server-side auto-refresh can resolve a DIFFERENT inline-adaptive height for the same handle; the widget now sizes its box reactively. Also documented: plugin 9.0.0 never auto-disposes a FAILED `AppOpenAd` load and its failure callback carries no ad reference — a plugin-side leak per failed app-open load that the seam cannot fix (file upstream; re-check on plugin bumps; RESEARCH §3).
**Consequences.** Seam tests cover all three (`inline adaptive refresh` and `load-dispatch failures` groups). `dimensions` is an additive interface member (fakes updated).

## ADR-049 — show() uses cheap live checks; the click latch gets a close-grace window  ·  accepted
**Context/Decision.** (a) `show()` ran the full `loadBlockReason` — config gate + consent settle — while already HOLDING the shared coordinator claim; an in-flight ADR-035 consent retry (network-bound, 30s timeout) froze every full-screen format behind one call. A warm handle proves config+consent were satisfied at load time, so `show()` now uses `AdGate.showBlockReason`: enabled + a LIVE `canRequestAds()` read (a withdrawal between load and show is still respected), never a settle join. (b) The ADR-042 click latch was cleared only by a foreground event; an iOS in-app overlay click (open→close, NO foreground event ever) stranded it, eating the next genuine warm return's app-open impression. `onAdClosed` now starts a 3-second grace clock (lazy read, no timer): a foreground event inside it still counts as the return-from-ad (Android's external-browser resume delivers close and foreground in ambiguous order — clearing immediately would re-open the ADR-042 hole); after it the latch expires.
**Consequences.** Guarded by the `show path is cheap` test and the coordinator latch group. `viewAdCloseGrace` is a coordinator constant (3s).

## ADR-050 — live ads come DOWN when no longer permitted (registry + recheckGate)  ·  accepted
**Context.** With `minRefresh` off by default (ADR-041), NOTHING re-checked a mounted banner/native ad's permission — while AdMob's server-side auto-refresh kept requesting ads for the mounted view. So `disableAds()` left a Remove-Ads purchaser watching (and earning from) the old banner; `dispose()`/re-`initialize` (ADR-044) left widget-owned controllers serving through a dead graph; and a consent withdrawal via the privacy-options form was entirely unobservable.
**Decision.** New `AdController.recheckGate()` (drop a live/warm ad whose permission is gone; load when newly permitted). `AdFlow` tracks minted view controllers (deregistered via an `onDisposed` hook) and re-checks everything on `enableAds`/`disableAds`, after any consent mutation through `AdFlow.consent` (now a thin `_GraphAwareConsentGateway` wrapper — chosen over adding members to the public `ConsentGateway` interface, which would break external implementers), and on `dispose` (whose gate also hard-refuses: `isEnabled => !_disposed && …`). `enableAds()` re-warms immediately.
**Consequences.** BEHAVIOUR CHANGE (documented in MIGRATION). Guarded by `test/facade/lifecycle_drop_test.dart` (6 tests, red pre-fix). Apps must use `ads.consent` (not a hand-built gateway) for the reactive withdrawal path — README says so.

## ADR-051 — full-screen preloads expire: shared maxAdAge with proactive replacement  ·  accepted
**Context.** Google documents full-screen ads as expiring after ~1 hour (4h app-open); a stale ad may fail to display or display without counting. Only app-open enforced an age — an interstitial preloaded at session start and shown hours later was revenue-dead inventory occupying the slot's one natural break.
**Decision.** Generalized app-open's `_loadedAt`/`isExpired` into the base: every load timestamped; `show()` discards-and-reloads an expired ad; an expiry timer (sharing the single `_timer` slot — safe, since no other timer runs while `AdLoaded`) proactively replaces a warm ad that goes stale. `maxAdAge` on the three configs (default 55min; null disables); `AppOpenConfig.expiry` feeds the same mechanism, so a >4h background return now finds a FRESH ad more often instead of sacrificing the first return to discard-and-reload.
**Consequences.** DEFAULT/BEHAVIOUR CHANGE. Timers don't run while suspended, so the show-time check remains the guarantee. Guarded by `full_screen_expiry_test.dart` (verified red against a neutered fix). RESEARCH §3 records the ground truth.

## ADR-052 — runtime SSV updates; observability (paid-event slot + AdResponseSummary)  ·  accepted
**Context/Decision.** (a) SSV was frozen at load from const config, but apps learn `userId` at login and per-show `customData` moments before `show()` — the exact high-value flows SSV exists for. Both rewarded controllers gain `setServerSideVerification(ssv)`: applies to the WARM ad (new seam handle method → the plugin's `setServerSideOptions`, legal any time before show) and to future loads; unlike the silent best-effort attach at load (failing a load over SSV would cost the ad), the explicit update RETHROWS. (b) `AdPaidEvent` gains `slot` (tagged by the owning controller) and `adSourceName` (read from `ResponseInfo` at event time — the winner for THIS impression); new `AdResponseSummary` (`handle.response`/`controller.response`) surfaces responseId/adapter/winning source. Without these there was no way to log a standard analytics `ad_impression` or attribute fill per network through ad_flow at all.
**Consequences.** Additive; the seam handle interfaces grew members (fakes updated; noted for rare external implementers). Guarded by `observability_test.dart` + seam SSV-ordering tests.

## ADR-053 — fail-fast config validation; null-safe slot getters; primer first-frame wait  ·  accepted
**Context/Decision.** (a) `AdFlowConfig.validate()` (run by `initialize`): empty ad-unit strings, no-platform slots, negative/zero durations, non-positive `maxInlineHeight` → `AdFlowError(invalidConfig)` at init instead of silent production no-fill; Durations cannot be compared in const asserts, so runtime validation is their only home. (b) `…OrNull` getters for every full-screen slot: the throwing getters are right for misconfiguration, but a slot absent BY DESIGN (single-platform ad units) made shared code crash — the README's own snippet did, on iOS. (c) The consent/ATT primers `await` a bounded (5s) first-frame wait: the ADR-032 background flow could reach a primer before the navigator mounted, and the presenter's own context-null guard silently dropped it on the one launch that matters; injectable for tests, no-op headless. (d) `PrivacyOptionsButton` failures default to `FlutterError.reportError`; `whenReady` documented as a one-shot snapshot.
**Consequences.** All additive. Guarded by config validation tests and the primer plumbing's existing suite.

## ADR-054 — seeded random-interleaving fuzz as a permanent regression net  ·  accepted
**Context.** The suite's bug history is illegal-interleaving bugs found one at a time (ADR-024, review findings #3/#4, ADR-046). Hand-enumerated interleavings always trail the next one.
**Decision.** `state_machine_fuzz_test.dart`: 24 seeds × 120 random ops per controller (banner + interstitial) inside fakeAsync — public API calls, SDK event injection, hold/release, failure toggles, gate flips, clock/timer advances — with invariants asserted after every op: at most one live handle and it is the current one; `AdLoaded` implies a handle; the coordinator claim tracks `AdShowing`; dispose leaves nothing live. Failures print the seed and replay deterministically.
**Consequences.** Any future interleaving bug in these controllers has a standing chance of being caught without anyone thinking of it first. Extend the op set when new operations are added (SKILL §6 note).

## ADR-055 — 3.0.0: the compat-forbidden cleanup, and the redesigns deliberately rejected  ·  accepted
**Context.** The maintainer explicitly lifted the backward-compatibility constraint ("limited public adoption; best long-term design wins"), with the counter-rule that breaking changes must earn their keep. Reviewed the whole architecture against that freedom.
**Decision — what breaks (each one a documented 2.x wart):**
1. **`AdBlocked(reason)` joins `AdLoadState`.** ADR-045 called this the correct model and shipped a parallel diagnostic channel only because a sealed-type addition breaks exhaustive switches. Blocked-on-LOAD is now a state (consent pending / Remove-Ads / withdrawal / disposed graph are visibly different from "nothing requested"); blocked-on-SHOW still reports via `noteBlocked` (a show refusal never changes load state — e.g. a capped show leaves `AdLoaded`).
2. **Widget-first ad widgets.** `AdFlowBanner(adFlow:)`/`AdFlowNativeAd(adFlow:)` create AND own their controllers, making the ADR-029 footgun unrepresentable; `controller:` stays for advanced use.
3. **`show()` honesty.** The base interface no longer carries a reward callback that interstitial/app-open silently ignored; the engine moved to a protected `showEngine`, and the rewarded formats keep `show({onReward})`.
4. **`AdGate` purified.** `canShow` (review finding #6's racy composed query, zero in-package callers since ADR-024, kept in 2.x only as public API) is deleted along with the gate's now-unused caps/coordinator collaborators — the gate answers PERMISSION; the controllers own show pacing (where the atomic `tryEnter()` lives).
5. **Deletions/renames:** `AppOpenConfig.showOnColdStart` (ignored since ADR-043) removed; banner/native `slot` → `slotName`.
6. **Additive:** `AdFlow.canRequestAds` (`ValueListenable<bool>`), the LIVE consent answer — closes the `whenReady`-staleness finding properly instead of doc-only.
**Decision — what was considered and REJECTED (breaking with no meaningful benefit):**
- A synchronous `AdFlow initialize()` return: ADR-032's reasoning (fail-fast as a rejected Future; `await_only_futures` churn at every call site) holds independent of compat.
- Stream-based events over `ValueListenable` (ADR-005 stands), merging policies into controllers, any layer reshuffle, renames-for-taste. The architecture's bones — seam, DI, policy layer, non-blocking init with structural gates — were validated by two audits and a documented bug history; a rewrite would destroy verified value.
**Consequences.** Version **3.0.0** (folding the unpublished 2.2.0 hardening in). MIGRATION.md's 2.x → 3.0 checklist is five mechanical items. The example and README teach the widget-first path as primary.

## ADR-056 — nothing throws its way into a wedge: gate containment + app-callback isolation  ·  accepted
**Context.** 4.0 audit. The permission gate's collaborators throw in the wild (the plugin's UMP getters force-unwrap channel results — verified in the 9.0.0 source; an injected gateway can reject through `_settleConsent`), and every controller awaited the gate OUTSIDE its load `try`. One throw pinned the slot at `AdLoading` forever (the re-entry guard then refuses every later load) with an unhandled async error on top. App callbacks (`onAdBlocked`, `onPaidEvent`, reward grants) ran unguarded inside state transitions, so an app bug corrupted the transition that invoked it.
**Decision.** (a) `AdGate.loadBlockReason`/`showBlockReason` never throw: contained → reported via `FlutterError.reportError` → answered as new `AdBlockReason.internalError`. (b) Indeterminate is ASYMMETRIC: it blocks new loads (safe) but never drops a live ad (recheck/refresh keep the mounted ad on `internalError`; the banner refresh loop re-arms rather than dying). (c) Controllers wrap the whole load body in ONE try. (d) `guardedCallback` isolates every app-supplied callback through `FlutterError.reportError` — visible, never corrupting. (e) The gateway's final `canRequestAds()` read honours "never throws" (lastError + false).
**Consequences.** `AdBlockReason.internalError` is public (enum addition → 4.0). Guarded by `error_containment_test.dart` (gate-throw + app-callback groups).

## ADR-057 — per-load watchdog (RetryConfig.loadTimeout)  ·  accepted
**Context.** The plugin has NO load timeout of its own and never cleans up a load whose callback never arrives (verified in source: no timer anywhere; `_loadedAds` entry removed only by dispose). A dropped channel callback, hung SSV attach or hung `getPlatformAdSize` left the awaiting controller at `AdLoading` for the session.
**Decision.** Every controller load await is bounded by `watchAdLoad` (`RetryConfig.loadTimeout`, default 60s — far above any legitimate no-fill answer; null disables). Timeout → `AdFlowError(timeout)` into the normal retry path. A LATE completion is disposed, never installed — structurally: the only code that installs handles is the load continuation, which already took the timeout branch, so no generation counters are needed.
**Consequences.** New failure mode visible as `AdFailed(timeout)`. Guarded by `load_watchdog_test.dart`.

## ADR-058 — SSV is fail-closed at load  ·  accepted
**Context.** The seam attached SSV inside `try { setServerSideOptions } catch (_) {}` — a detectable attach failure was swallowed and the ad served as ready; the user earned the reward and the publisher's SSV endpoint got a callback with no userId/customData to validate. Plugin-source fact: the native handlers ack the SSV call unconditionally (`result.success` even on the logged null-ad branch), so only channel-level faults are detectable client-side.
**Decision.** An SSV-configured load whose attach fails is DISPOSED and FAILED (`AdFlowErrorKind.ssv`, enum addition); the controller's retry reloads and re-attaches. Docs state the detectability limit honestly (the ack is not proof; the SSV endpoint is). `updateServerSideVerification` keeps its rethrow contract.
**Consequences.** Behavior change; guarded at seam (`gma_ad_sdk_test.dart` SSV group) and controller level; `FakeAdSdk.ssvAttachError` mirrors it.

## ADR-059 — rewarded-interstitial show is an atomic reservation; RI joins the global cap  ·  accepted (revises ADR-039 for RI)
**Context.** The intro ran BEFORE consent/cap/pacing/coordinator checks: a user could accept and then be refused ("no ad, no reward, no explanation"). The claim was taken only after the intro, so a warm return could stack an app-open ad OVER the intro; the expiry timer could discard the handle mid-intro; a throwing presenter rejected `show()`.
**Decision.** `showEngine` gains a `confirm` hook that runs with all checks passed and the claim held (state `AdShowing` spans the whole sequence); skip/throw rolls back to a warm `AdLoaded`. And the RI slot is REMOVED from `globalCapExemptSlots`: ADR-039's "user-initiated" reasoning conflated the ad with the sequence — the INTRO is the involuntary interruption, and with preflight-before-intro a capped sequence never starts, so the exemption's original justification (accepted-then-refused) no longer exists. Classic rewarded (explicit user tap) stays exempt; both formats still record globally.
**Consequences.** Behavior change (documented). Guarded by the RI `atomic show reservation` group + `cap_semantics_test.dart`.

## ADR-060 — frequency caps are memory-authoritative; persistence is serialized write-behind  ·  accepted
**Context.** Controllers record impressions un-awaited at dismiss, but minGap/hourly checks READ the store — a check racing an in-flight write let two full-screen ads run back to back across formats; concurrent records raced read-modify-write and lost impressions on disk.
**Decision.** In-memory state is the single source of truth: hydrated LAZILY once (first use, in the caller's zone — a constructor-kicked future cannot be driven from a test's fakeAsync zone), bounded 5s (hanging/corrupt store → session-only capping, never blocked shows). After hydration, decisions/mutations are synchronous; `recordImpression` commits to memory before its first await (its returned future = durability). Persistence is a serialized snapshot chain; a throwing store breaks nothing. ADR-037 clock guards preserved.
**Consequences.** Impressions in the last moments before process death may not persist (slightly loose cap after a crash) — the correct trade against wrong in-session decisions. Guarded by the `memory-authoritative decisions` group.

## ADR-061 — request configuration is a retried process with an explicit failure policy  ·  accepted (supersedes the ADR-033 addendum's silent fail-open)
**Context.** A failed/timed-out `updateRequestConfiguration` released a one-shot gate in a `finally`: every load that session went out WITHOUT COPPA/under-age tags, content rating or test-device registration — silently, unrecoverably. Worse, config was dispatched immediately after a TIMED-OUT init: exactly the window where native init may still be mid-bootstrap on the platform thread — the ADR-028 deadlock, quietly re-opened for the slowest devices.
**Decision.** `RequestConfigFailurePolicy {auto, failOpen, failClosed}` (default auto = fail-closed iff `requestConfigIsPolicySensitive`). The apply is rate-limit retried; every gate check JOINS the bounded attempt; blocked slots show `AdBlocked(requestConfigNotApplied)` and recover on their own backoff. An attempt NEVER dispatches while init is in flight: it joins a pending init for 2s (the normal first-frame case proceeds inline — preserving ADR-033's config-before-load), a hung init fails attempts fast into visible AdBlocked, and an init-completion hook applies config whenever init finally lands. `AdGate` takes `settleRequestConfig` (callback) instead of `configReady` (future). UI is never blocked; `whenReady` stays bounded (~30s worst).
**Rejected:** always-fail-open (silent policy degradation — the audit's core objection); always-fail-closed (kills revenue for apps whose config is vacuous); blocking `initialize()` on config (v1's splash hang).
**Consequences.** Guarded by `request_config_policy_test.dart` (+ the two rewritten ADR-033 tests). Enum addition → 4.0.

## ADR-062 — honest mediation surfaces; no "UMP handles it all" claim  ·  accepted
**Context.** Web-verified against current Google docs: *"You are responsible for verifying consent is propagated to each ad source… Google is unable to pass the user's consent choice to such networks automatically"* (Unity/Meta partner pages). AppLovin 12+ reads TCF; Unity needs MetaData calls; Meta needs AC + pre-init LDU; AppLovin US-state flags must precede GMA init. ad_flow's docs claimed "Nothing to do in ad_flow", and the code had no surface to do it anyway (full-screen requests hardcoded `const AdRequestOptions()`).
**Decision.** (a) Per-slot `AdRequestOptions request` on every format config; `MediationNetworkExtras` seam type → plugin `mediationExtras`. (b) `AdFlow.onConsentChanged` fires (isolated) after every consent flow/mutation — the forwarding point. (c) `AdFlowConfig.deferMediationInit` → seam `disableMediationInitialization()` before init (plugin-verified to exist on both platforms) for partners needing pre-init flags after consent. (d) MEDIATION_SETUP.md rewritten around the honest contract (what UMP writes, which SDKs read it, what stays the integrator's). README/pubspec "policy-compliant" absolutes softened to policy-AWARE with the dependency on placements/console stated.
**Consequences.** `AdSdk` interface grew one member (implementer note). The package now describes exactly what it guarantees.

## ADR-063 — 4.1.0 post-release audit: no silent failure, take two  ·  accepted
**Context.** An independent adversarial re-audit of the published 4.0.0 (multi-agent verification, 24 confirmed findings, 11 surviving adversarial refutation) found a second tier of the same class of defect 4.0 targeted: paths that fail SILENTLY or race, rather than crash. All fixes are additive/non-breaking (4.1.0).
**Decisions (one invariant each, all fail-first + neuter-verified where a debug repro exists):**
- **Awaited consent-forwarding barrier (headline).** `onConsentChanged` is a fire-and-forget `void` hook: it only SCHEDULES the app's async forwarding and is assignable only after `initialize` returns, so a mediation network that reads its privacy signal at request time could receive the first ad request BEFORE the signal was forwarded, and the INITIAL consent flow's dispatch could be lost entirely. New additive `forwardConsent: Future<void> Function()?` on `initialize`: `_runConsent` now publishes on `_consentInFlight` (the future `AdGate._settleConsent` joins) a CHAIN that resolves only after forwarding, with `_consentOpen` set at the end of the chain — so the first load cannot open the gate before forwarding ran. Bounded (`_forwardConsentTimeout` 15s → degrade open, never hang, consistent with `_settleRequestConfig`) and error-contained. Default (no forwarder) is byte-for-byte prior behaviour. The naive alternative — making `onConsentChanged` itself awaitable and joining it in `showBlockReason` — was REJECTED: it would reintroduce the ADR-028 hang class on the show path.
- **Frequency-cap late-hydration overwrite.** `.timeout` does not cancel the underlying `_hydrateSlot` reads; a store that hung past the 5s bound then resumed ran its `_history[slot]=…; _last[slot]=…` writes LATE, rolling an in-session impression's last-stamp back to a stale prior-session value → two full-screen ads back to back. Once `_hydrationDone`, a late read MERGES (union history, keep the more-recent non-future last-stamp) instead of overwriting — memory is never rolled back, and a merely-slow store still recovers cross-session capping. (Chose merge over the simpler "skip late read" so a slow-but-working store does not silently lose cross-session minGap.)
- **Runtime SSV in-flight race + fail-drop.** `setServerSideVerification` during an in-flight load set the override for future loads and returned success, but the pending load installed an ad carrying the PREVIOUS payload. Extracted a `RuntimeSsvController` mixin: it re-applies the latest override to the ad the moment it installs (`onLoaded`), and DROPS a warm ad whose direct update failed (so it can never show with stale verification) before rethrowing.
- **Rewarded-interstitial post-intro re-validation.** The unbounded intro ran BEFORE the checks stayed valid; a Remove-Ads purchase or the ad aging past `maxAdAge` during it was ignored. `showEngine` re-runs the cheap live `showBlockReason` + `isExpired` after the confirm hook, rolling back rather than showing. `internalError` is treated as proceed (a transient blip must not waste an accepted intro).
- **Callback isolation completeness.** `guardedCallback` now contains an ASYNC callback's later rejection (invoked through `Function` to recover the runtime `Future` and attach `catchError`); the refreshed-banner paid-event subscription routes through the guarded `_dispatchPaid` (it used a raw closure); new `safeUnawaited` contains a rejecting `dispose()`/`cancel()` during teardown.
- **`validate()` mirrors every constructor assert** (stripped in release): cap `maxPerSession`/`maxPerHour >= 0`, `RetryConfig.maxAttempts >= 0` / `jitterFactor ∈ [0,1]`, `minActionsBetween >= 0`, native exactly-one.
- **Observability:** `deferMediationInit` failure is REPORTED, not swallowed; `MediationNetworkExtras` asserts non-empty class names (a silent reflection no-op otherwise).
**Consequences.** Version 4.1.0 (additive). New public surface: the optional `forwardConsent` param. Guarded by `consent_forwarding_test.dart`, the new groups in `frequency_cap_policy_test.dart` / `rewarded_ad_controller_test.dart` / `rewarded_interstitial_ad_controller_test.dart` / `banner_refresh_test.dart` / `callback_guard_test.dart`. Two verifier scope-corrections recorded and honoured: the consent-withdrawal-during-intro half is essentially unreachable (UMP form cannot be foreground under the intro), so the RI re-check's value is the Remove-Ads/expiry half; the SSV race window is only the load round-trip (medium, not high).
## ADR-064 — consent forwarding + deferral fail CLOSED by default (5.0.0 release gate)  ·  accepted (corrects ADR-063's degrade-open forwarding)
**Context.** A release-gate review of ADR-063 flagged its consent-forwarding barrier as unsafe by DEFAULT: it degraded OPEN on a forwarder failure/timeout (15s), so a mediation partner that reads its GDPR/US-state/age signal at request time could still receive an ad request WITHOUT that signal — the exact policy exposure the barrier exists to prevent. Likewise, ADR-063 only REPORTED a `deferMediationInit` failure; reporting does not preserve the pre-init ordering the caller explicitly requested. "Bounded, degrade-open" is the right default for request CONFIG loss of low-sensitivity fields, but not for a privacy signal a partner legally requires.
**Decision.** Consent forwarding is now a fail-CLOSED gate barrier, mirroring `RequestConfigFailurePolicy` (ADR-061):
- Forwarding moved OUT of the `_runConsent` chain into a dedicated `AdGate` barrier (`settleConsentForwarding`) checked AFTER consent is granted, BEFORE the mediation-capable request. Benefit: `whenReady`/UI never wait on forwarding (only the ad request does), and forwarding runs lazily once per consent generation, joined by concurrent loads.
- **Fail-closed by default** (`AdFlowConfig.mediationConsentPolicy = MediationConsentFailurePolicy.failClosed`): a failed/timed-out/absent forward BLOCKS the load with the new `AdBlockReason.consentNotForwarded`, retried in the background (rate-limited), recovering the moment forwarding succeeds. `.failOpen` is the explicit, deliberately-hard-to-select-by-accident revenue-first opt-out (only safe when every network reads the IAB string itself).
- **Deferral:** retried 3× before `initialize()` (the plugin no-ops it after); a definitive failure sets `_mediationDeferralFailed` and, being unrecoverable, blocks mediation-capable loads under fail-closed (the requested ordering is permanently lost). `.failOpen` serves anyway.
- **Generation counter:** every consent flow AND every privacy-options mutation invalidates the forwarded state (`_invalidateConsentForwarding` bumps `_consentGeneration`), so (a) the barrier re-establishes before the next newly-permitted load — not only at startup — and (b) a forward that raced a mutation cannot mark the NEW generation forwarded (latest-value-wins).
**Rationale.** The invariant the maintainer set: when a publisher opts into forwarding/deferral, the package must NOT silently make a mediation-capable request after forwarding/deferral failed; UI stays non-blocking; ad requests may fail closed and retry; any fail-open must be explicit and unmistakably unsafe. Degrade-open violated it; fail-closed honours it while keeping UI non-blocking (the barrier gates the request, never `initialize`/`whenReady`).
**Rejected alternatives.** (a) Keep degrade-open with a louder log — still ships an unsignalled request by default. (b) Block `initialize()`/`whenReady` on forwarding — reintroduces v1's splash hang (ADR-032). (c) Permanent hard-block on ANY forward failure with no retry — kills recoverable transient failures; the retry+recover path is strictly better for the common case.
**Consequences.** Version **5.0.0**: `AdBlockReason.consentNotForwarded` is an enum case (breaks exhaustive switches, like the 4.0 additions), and forwarding's default changes for adopters. Non-adopters (no `forwardConsent`/`deferMediationInit`) are byte-for-byte unaffected. New public API: `MediationConsentFailurePolicy`, `AdFlowConfig.mediationConsentPolicy`, `AdBlockReason.consentNotForwarded`, `AdGate.settleConsentForwarding` (constructor param). **Release-gate review addendum.** A 4-dimension adversarial workflow (19 agents) confirmed the fail-closed invariant is UPHELD with no blocker/major defect, and independently validated the regression tests as non-vacuous (generation guard, SSV latest-wins, async-callback containment, cap set-union dedup). One minor finding fixed: `_invalidateConsentForwarding` originally nulled `_forwardAttemptInFlight`, orphaning an in-flight forward so a post-mutation load on a fresh slot could launch a SECOND concurrent `forwardConsent` invocation (internal state stayed correct via the generation guard; the hazard was an undocumented reentrancy requirement on the app callback). Now the in-flight attempt is left in place so a post-mutation load JOINS it — at most one forward call in flight. Also hardened proactively during the same pass: the barrier awaits a `_deferMediationSettled` completer so a load can never slip past while the deferral is still in flight (structural, not timing). Guarded by the rewritten `consent_forwarding_test.dart` (fail-first + neuter-verified: forcing fail-open makes the blocking tests red), plus release-gate adversarial suites: `async_callback_containment_test.dart` (async rejection through the real public void-typed callbacks), SSV latest-value-wins/dispose-race group in `rewarded_ad_controller_test.dart`, and the merge-dedup test in `frequency_cap_policy_test.dart`.
## ADR-065 — remove deferMediationInit; forward consent BEFORE initialize; serialize the forwarder source; invalidate stale-consent ads (release gate)  ·  accepted (supersedes ADR-064's request-time-only model)
**Context.** A second release-gate review re-opened ADR-064 with three findings, all confirmed against current official Google docs and the plugin's native source:
1. **`disableMediationInitialization` is not a defer/resume — it is a session-wide DISABLE.** Verbatim (Android `MobileAds` ref): "Call before `initialize()` or the first ad request to disable mediation adapter initialization. This method is a noop once `initialize()` or the first ad request is made." + "should only be called if... you don't plan to use Google mediation during this app session (for example, you are running an A/B test)." iOS mirrors it. The plugin has NO resume API (verified in `mobile_ads.dart` / native handlers). Mediation adapters initialize DURING `MobileAds.initialize()` (AdMob mediation guide: "During that initialization call, mediation adapters also get initialized"), and AppLovin/Meta require their privacy flag set BEFORE that init ("before you initialize the Google Mobile Ads SDK"). So `deferMediationInit` was conceptually invalid AND revenue-harming (it disables Google mediation), and the only correct pattern is to set the flag before `initialize()`.
2. **`Future.timeout` does not cancel its source.** ADR-064 wrapped the forwarder in `.timeout(15s)` and tracked the timeout-wrapped attempt; on timeout the attempt resolved, the source kept running, and a retry could invoke `forwardConsent` again concurrently — and an older consent operation could apply its external partner-SDK side effect AFTER a newer one. The generation guard protected only ad_flow's internal state, not the external side effect.
3. **Already-loaded ads across consent generations stayed privacy-stale.** A warm full-screen ad or visible banner/native loaded under consent state A kept rendering/measuring under A after a mutation to B (full-screen `recheckGate` used the permission-only `showBlockReason`; a non-forwarding app's gate never blocked).
**Decisions.**
- **Removed `AdFlowConfig.deferMediationInit`, `AdSdk.disableMediationInitialization`, `GmaAdSdk` impl, fake knobs.** `forwardConsent` now runs BEFORE `_sdk.initialize()`: `_start` gathers consent → runs the forwarder → then initializes the GMA SDK, so a partner's flag precedes its adapter init. Fail-closed: on forward failure the SDK is NOT initialized and loads block (`consentNotForwarded`), retried in the background; init runs when forwarding succeeds. `failOpen` initializes anyway. Non-adopters keep parallel init (ADR-028/032). UI non-blocking: `initialize()` returns immediately; only `whenReady`/loads wait. The forwarding gate barrier also awaits the init pipeline before letting an adopter's load fire (the config gate can't be relied on for adopters, since init is gated on forwarding).
- **Source serialization.** Track the un-timeout'd forwarder invocation in `_forwardSource`; the gate's `.timeout` bounds only the WAIT, never the source. At most one `forwardConsent` is ever in flight — even across the timeout boundary — and a newer-generation forward starts only after the older source completes, so external partner-SDK side effects are strictly ordered (no older-after-newer).
- **Stale-consent invalidation.** New `AdController.invalidateForConsentChange()`: after a consent/privacy mutation, a warm (not-yet-shown) full-screen ad or a visible banner/native ad is dropped and reloaded through the fresh (re-forwarded) gate; a full-screen ad ON SCREEN is not interrupted (its impression already fired). `_afterConsentMutation` drives it.
**Rejected.** Keeping `deferMediationInit` deprecated (it is a footgun that disables Google mediation and cannot achieve the ordering goal); a request-time-only barrier (insufficient for init-time partners — adapters init during `MobileAds.initialize()`, before any request); interrupting a showing full-screen ad on a mutation (worse UX; the impression already happened).
**Consequences.** Version stays **5.0.0** (already major; `deferMediationInit` removal + `AdController.invalidateForConsentChange` addition fold into it). Guarded by the rewritten `consent_forwarding_test.dart` (forward-before-init ordering, timeout-boundary serialization, out-of-order side-effect prevention) and `consent_stale_ad_invalidation_test.dart` — each fail-first + neuter-verified. **Release-gate review #2 addendum.** A 4-dimension adversarial workflow (18 agents) confirmed all four core invariants UPHELD (no adopter request before init; init gated on forwarding fail-closed with recovery and no whenReady hang; at most one forwardConsent in flight strictly ordered; showing full-screen ads never interrupted, no leaks). One minor gap fixed: the MID-LOAD window — a consent mutation landing while an ad is `AdLoading` (its gate already passed under generation N) made `invalidateForConsentChange` a no-op, so the load installed a stale-consent ad. Fixed by generation-stamping: `AdGate.consentGeneration` (wired to the facade's `_consentGeneration`) is captured when a controller dispatches its SDK request and compared on completion; if it advanced, the ad is dropped UNSHOWN and reloaded through the re-forwarded gate (covers full-screen load, banner load + refresh swap, native load). Guarded by controller-level fail-first tests in `consent_stale_ad_invalidation_test.dart`. Honesty note documented: forwarding re-establishes on a mutation only for REQUEST-time partner reads; an already-initialized adapter cannot be re-initialized, so init-time flags are set once, before the first init.
## ADR-066 — simplification pass: fold stale-consent invalidation into `recheckGate`; rename `failOpen → unsafeFailOpen` (5.0.0, post-redesign)  ·  accepted (supersedes ADR-065's separate `invalidateForConsentChange` method)
**Context.** The ADR-065 redesign is accepted and correct, but a maintainability review of the final diff found accidental complexity: it added a SECOND public interface method — `AdController.invalidateForConsentChange()` — that did the same drop-and-reload job as the existing `recheckGate()`, driven from a SECOND facade fan-out (`_invalidateLoadedAdsForConsentChange`) called alongside `_recheckAll` from `_afterConsentMutation`. Two methods, two fan-outs, two per-controller implementations, for one concept ("this ad's gate context changed — re-evaluate it"). The mid-load window already used an INTERNAL generation stamp; only the already-warm case used the public method.
**Decision.** Unify on the mechanism that was already internal:
- **Removed `AdController.invalidateForConsentChange()`** and all three implementations. The already-warm stale-consent drop is folded into the existing `recheckGate()`: each controller stamps `_loadedGeneration` when an ad installs, and `recheckGate`'s `AdLoaded` branch drops-and-reloads when `_gate.consentGeneration` has advanced past it — BEFORE the permission check (a stale ad that is still *permitted* must still be dropped). `recheckGate` already ran after every consent mutation (via `_recheckAll`), so no new call site is needed. Net: **no new public interface method vs v4.0.0** (`recheckGate` shipped in 4.0; its behavior expanded, its signature did not).
- **Removed the facade's `_invalidateLoadedAdsForConsentChange`**; `_afterConsentMutation` now calls only `_recheckAll()`. One owner for "re-evaluate every controller against the current gate."
- **Renamed `MediationConsentFailurePolicy.failOpen → unsafeFailOpen`** (unreleased 5.0 enum; free rename). The `unsafe` prefix makes the revenue-first opt-out impossible to reach for without noticing — no machinery added, just a name. (`RequestConfigFailurePolicy.failOpen` is untouched: it shipped in 4.0 and its loss is low-sensitivity config fields, not a partner privacy signal.)
**Ownership map (one owner each, no duplication).** Forwarding state / serialization / retry / recovery → `AdFlow` (`_forwardSource`, `_consentForwarded`, `_forwardRetryArmed`, `_forwardRetryTimer`, `_consentGeneration`). The generation *compare* → `AdGate.consentGeneration` (already-public class; a per-file-library language constraint forces the getter to be public for controllers to read it — it is an optional constructor callback defaulting to `0` = no-op, never an integration step). Stale/permission re-evaluation of a loaded ad → each controller's `recheckGate` + `_loadedGeneration` stamp.
**Retained complexity (deliberate) + its invariant.** (a) `_loadedGeneration` per controller — INVARIANT: an installed ad's impression/measurement must reflect the consent generation it was requested under; a later generation drops it. (b) `AdGate.consentGeneration` optional callback on the public gate — INVARIANT: the mid-load window (gate passed under gen N, ad installs after a mutation to N+1) drops UNSHOWN; cannot be internalized further without a new collaborator (more complexity, not less). (c) Source serialization (`_forwardSource` un-timeout'd) — INVARIANT: `Future.timeout` does not cancel its source, so at most one `forwardConsent` runs at a time and external partner side effects stay strictly ordered. A permanently-hung source therefore fails CLOSED forever by design (documented on the field): it is never cancelled or retried concurrently, so a broken forwarder blocks mediation loads (recoverable only if the source itself completes) rather than risking an out-of-order side effect — the safe direction.
**Rejected.** Keeping both methods "for clarity" (two paths for one concept is the accidental complexity, not clarity); making the consent generation a first-class public integration surface (no real adopter use case — it is internal wiring the facade owns); a cancellation framework for a hung forwarder (large machinery for a case where fail-closed is already the safe outcome — documenting the behavior is the right weight).
**Consequences.** Version stays **5.0.0**. Final public API delta from v4.0.0: **removed** `AdFlowConfig.deferMediationInit` AND `AdSdk.disableMediationInitialization()` (the seam method it drove — a breaking change for any direct `AdSdk` implementer; the shipped `FakeAdSdk` and `GmaAdSdk` are updated); **added** `AdBlockReason.consentNotForwarded`, `MediationConsentFailurePolicy {failClosed, unsafeFailOpen}`, `AdFlowConfig.mediationConsentPolicy`, `AdFlow.initialize(forwardConsent:)`, and two optional `AdGate` constructor callbacks (`settleConsentForwarding`, `consentGeneration`) + the `AdGate.consentGeneration` getter. No barrel export was added or removed. The `AdController` interface is UNCHANGED from v4.0.0. Verified: `dart format` + `flutter analyze` clean, 494 tests green (the whole-AdFlow stale-ad tests drive the folded path through `showPrivacyOptions()`; mid-load tests through `AdGate(consentGeneration:)`), pana 160/160, dry-run 0 warnings, Android + iOS example builds.

## ADR-067 — App Open trigger modes + explicit one-shot cold-launch opportunity (5.1.0)  ·  accepted
**Context.** App Open ads serve two legitimate product moments — a genuine background→foreground return AND a cold process launch (a startup/loading experience) — but the manager only ever showed on a warm return. There was demand to support cold-launch shows, and the standard wrong way is to fake a cold-launch foreground event. That is unsound here: `AppStateEventNotifier` does NOT emit a cold-launch foreground (the seam calls `startListening()` only once the app is already foregrounded — RESEARCH §, SKILL §6), so nothing to hook, and hanging a splash on "wait until an ad loads" is exactly v1's splash hang / the non-blocking-init regression (ADR-032) we must never reintroduce.
**Decision.** A small, additive, backward-compatible surface:
- **`AppOpenTriggerMode {launchOnly, resumeOnly, launchAndResume}`** on `AppOpenConfig.triggerMode`, default **`resumeOnly`** (the exact v5 behaviour). `_onForeground` shows on a warm return only for `resumeOnly`/`launchAndResume`; `launchOnly` keeps one warm but never auto-shows.
- **`AppOpenAdManager.showAtLaunchIfReady() → Future<bool>`**, the explicit cold-launch path. Semantics: shows an **already-ready** eligible ad (delegating every policy — consent, caps, coordinator, expiry, Remove-Ads — to the controller's `show()`); returns `false` **immediately** if nothing is warm (NEVER awaits network/UMP/SDK/load); **one-shot per process launch**; a `false` result cannot become a surprise App Open once the user is in main content (the moment is spent even when not ready); a no-op under `resumeOnly`. The app calls it from its real loading screen, right before entering main content.
- **The one-shot latch is a PRIVATE process-global in an INTERNAL, non-exported file** — `LaunchLatch._consumed` (a `static bool` in `lib/src/lifecycle/launch_latch.dart`, which `ad_flow.dart` does not export). It must survive `AdFlow` reinitialization within a process (a second `initialize()` must not mint a second launch show), which cannot be expressed as injected instance state — so it is invariant 9's SECOND sanctioned exception (like `AdFlow._instance`), allow-listed in `no_global_state_test`. It is NOT exposed as public API (an earlier draft added a public `LaunchOpportunity` class + injectable constructor param; the release-gate review removed both — the launch latch is not something an app should inject). Tests reset it only through `ad_flow_testing.dart`'s `resetAppOpenLaunchOpportunity()`. (A prior draft used a `@visibleForTesting static resetLaunchOpportunity()` ON the exported `AppOpenAdManager` — but `@visibleForTesting` does NOT make a member private, so that reset was part of the production API; the final API-hygiene pass moved the latch into `LaunchLatch` and the reset into the testing barrel, leaving ZERO production-public reset surface.) The tests exercise the PRODUCTION default path (facade `initialize` + reinit), not an injected surrogate.
- **`launchOnly` retires inventory after its single launch** (`AppOpenAdController.retire()` → base `retireInventory()`): `load()` and the autonomous reloads (dismiss/expiry/retry) become inert and a warm non-showing handle is dropped, so it never keeps requesting an ad it can no longer show. A showing ad finishes on screen. `launchAndResume` does NOT retire (resumes need inventory); `resumeOnly` is untouched.
- Non-blocking first-frame is preserved: `showAtLaunchIfReady` never blocks on a load, and the example's `StartupScreen` renders immediately, does real frame-completion work, then takes the opportunity.
**Rejected.** Faking a cold-launch foreground via `AppStateEventNotifier` (the platform never delivers one; would only ever eat/duplicate a real warm return — same class of bug as the ADR-043 latch); a `showAtLaunchIfReady` that WAITS for a load (recreates the splash hang / blocks the first frame); a manual/explicit trigger mode beyond the three (no concrete use — added only for symmetry); a public `LaunchOpportunity` type/injection (an app has no reason to inject the process launch latch — a private static + a test-only reset is smaller and honest); persisting the one-shot across process restarts (each cold launch IS a new opportunity — an in-memory process latch is exactly right).
**Consequences.** Public additions only: `AppOpenTriggerMode` + `AppOpenConfig.triggerMode`, `AppOpenAdManager.showAtLaunchIfReady`, `AppOpenAdController.retire`, `FullScreenAdControllerBase.retireInventory` (`@protected`), and `AdFlowConfig.test(appOpenTriggerMode:)`. Default behaviour unchanged. Guarded by `app_open_trigger_mode_test.dart` (all modes, one-shot, not-ready immediate skip, consent closed, expired, reinit-via-static, dispose-before-launch, startup/resume collision, full-screen overlap, post-dismiss suppression, launchOnly inventory retirement) and a facade production-latch test; the one-shot latch and the retire mechanism are neuter-verified.

## ADR-068 — runtime SSV: finalize the loaded handle BEFORE publishing AdLoaded; generation-serialize updates (5.1.0)  ·  accepted (hardens ADR-058 / the 4.1 runtime-SSV mixin)
**Context.** `RuntimeSsvController` let an app set an SSV override (userId at login, per-show customData) on the warm ad and every future load. But the ad became showable carrying a **stale** payload: `load()` published `AdLoaded` and THEN re-attached the override in a post-publish `onLoaded()` hook, unawaited — so a state listener firing on `AdLoaded`, or an immediate `show()`, used the pre-update payload. Concurrent `setServerSideVerification` calls had no ordering guard, so a stale native completion arriving out of order (or a stale failure) could clobber the latest value or drop a valid ad.
**Decision.** Establish: **an ad is never externally ready or showable until the latest required SSV payload has settled successfully.**
- A NEW `Future<void> finalizeLoadedHandle()` (pre-publish, awaited) is ADDED alongside the existing `void onLoaded()` (post-publish). Both are kept — `onLoaded()` is exported public API (`FullScreenAdControllerBase` is barrelled, so its non-underscore members are public even though `@protected`), so it must not be renamed/removed (semver; corrected in the release-gate follow-up, ADR-067's sibling — see the compat test). Sequence: `load()` installs the handle + subscriptions, `await`s `finalizeLoadedHandle` BEFORE writing `AdLoaded`, then writes `AdLoaded`, then calls `onLoaded()` with its unchanged post-publish semantics. A finalize throw fails the load CLOSED (drop + retry, re-dispatching with the latest override) and disposes the installed handle/subscriptions exactly once; a consent mutation during finalize drops-and-reloads (mirrors the mid-load check). `showEngine`'s readiness gate is `!isReady` (equivalent to the old `!AdLoaded && handle` for the base).
- The mixin re-attaches a load-time override inside `finalizeLoadedHandle` (looping so an override set DURING finalization still lands), overrides `isReady` to report not-ready while a WARM-ad re-attach is in flight (`_attaching`), and stamps every update with a monotonic `_ssvGeneration` — only the latest generation's completion resolves readiness or (on failure) drops the ad, so reverse-order native completions cannot clobber the latest.
**Rejected.** Keeping the post-publish re-attach and blocking `show()` some other way (the ad is briefly showable-with-stale-payload no matter how you gate show — the only correct fix is not to publish `AdLoaded` until settled); serializing warm updates with an explicit queue (generation-guarding concurrent attaches is simpler and the method channel is already FIFO on the native side); a new `AdBlockReason` for "SSV settling" (an enum case is breaking in a minor — `notReady` is honest).
**Consequences.** No public API change (the base hook is `@protected`; `setServerSideVerification` keeps its signature). Config-time SSV, dispose safety, and the fail-closed/reload behaviour are unchanged. `FakeAdSdk` gains `onFullScreenHandleCreated` (test infra). Guarded by `runtime_ssv_race_test.dart` (5 adversarial cases, fail-first; finalize-before-publish neuter-verified) plus the existing runtime-SSV suite.

## ADR-069 — native ads expire (~55 min) and reload through the normal gate (5.1.0)  ·  accepted (generalizes ADR-051 to native)
**Context.** Google documents native ads as expiring after ~1 hour, but `NativeAdController` kept a loaded ad until manual `reload`/`dispose`. A long-lived screen (feed, home) could render revenue-dead — or policy-noncompliant — stale inventory indefinitely. The full-screen formats already had `maxAdAge` (ADR-051); native did not.
**Decision.** `NativeConfig.maxAdAge` (nullable, default **55 min**, consistent with the full-screen formats; `null` disables). The controller timestamps successful loads and arms an expiry timer on its existing single-slot `_timer` (while `AdLoaded` no retry/gate-recheck timer is pending; every transition out of `AdLoaded` — `reload`, `recheckGate` drop, `dispose` — reclaims it, so no leak or race). On expiry it drops the handle exactly once and reloads through the normal consent/config/retry gate; `isExpired` is the belt-and-suspenders for a timer that could not fire while suspended (an overdue timer fires on resume). Injectable clock for tests.
**Rejected.** A background-load-then-swap (banner-style, ADR-041) — the requirement is "never keep rendering inventory beyond maxAdAge," so we must drop at expiry even before a replacement is ready (a brief placeholder at the ~55-min mark is correct; an expired ad should not render anyway); a generic cache/expiry framework — this controller owns exactly one ad.
**Consequences.** Additive: one nullable config field (+ validation + equality) and a `now` constructor param. Guarded by `native_ad_expiry_test.dart` (timer expiry, long-suspension resume, manual reload near expiry, disposal, consent withdrawal, failed replacement load — 7 cases, fail-first; timer neuter-verified). Note (test hygiene, SKILL §6): a `fakeAsync` `elapse` of hours against a CLOSED gate churns the gate-recheck retry densely — bound such elapses in tests.

## ADR-070 — Remove-Ads collapses view ads to zero; deterministic adaptive pre-load placeholder (5.1.1)  ·  accepted (corrects the ADR-050 kill-switch layout + the review-finding-#8 placeholder estimate)
**Context.** Real emulator screenshots surfaced two layout bugs. (1) After `disableAds()`, ADR-050 correctly DROPS a mounted banner/native ad, but the widgets kept reserving their placeholder height — so a Remove-Ads user still saw a blank ad-sized gap (and, in the example, the `SafeArea` bottom bar and the decorated native `Card` around the collapsed child stayed visible). (2) `AdFlowBanner` reserved a speculative adaptive placeholder — "15% of device height, clamped to 50–90dp" (review finding #8) — which on a Pixel emulator reserved MORE than the real 468×60 banner, and the "50–90dp" figure was itself stale (Google now documents large anchored adaptive as 50–150dp; the seam resolves via `AdSize.getLargeAnchoredAdaptiveBannerAdSize`). Loaded banners already follow `handle.dimensions` correctly; the bug was purely in the pre-load reservation and the disabled state.
**Decision.** A small, backward-compatible layout fix — no public API added or changed.
- **Remove-Ads → zero footprint.** `AdFlowBanner`/`AdFlowNativeAd` return `SizedBox.shrink()` whenever ads are disabled, checked BEFORE the loaded/placeholder branches so it wins in every state and overrides an explicit `placeholderHeight`. Two independent signals, either sufficient: in widget-first (`adFlow:`) mode the widget listens to `adFlow.adsEnabled` (via `Listenable.merge`, which tolerates a null entry in advanced controller mode), so the collapse is SYNCHRONOUS — on the frame `disableAds()` flips the notifier, not waiting for the async `recheckGate()`; and in either mode the `AdBlocked(AdBlockReason.adsDisabled)` state the recheck lands on. Re-enabling reloads through the facade's existing `_recheckAll()` → `recheckGate()` → `load()` path — exactly one reload, no widget-driven duplicate (the `LayoutBuilder` load-kick is latched on `_loadRequested`).
- **Deterministic pre-load placeholder (banner).** No device-height guessing. Fixed → exact configured height; large anchored adaptive → the documented **50dp floor** (`reservedHeight`), then the exact `handle.dimensions` once loaded; inline adaptive → **0** (its real height is unknown until `onAdLoaded`/`getPlatformAdSize`). Explicit `placeholderHeight` is still honoured for ordinary non-loaded states, `placeholderHeight: 0` opts into fully collapsed pre-load, and it is never honoured while `adsDisabled`. Native keeps its configured/template height for ordinary loading states (only the disabled collapse is new).
- **Example.** `bottomNavigationBar` returns `SizedBox.shrink()` BEFORE constructing `SafeArea` (a collapsed child inside a retained `SafeArea` still reserves the inset); the native `Card` (title, padding, border) is hidden entirely — demonstrating that parent decorations must be hidden too. Corrected the stale App Open subtitle (the example runs `launchAndResume`, so "never on a cold launch" was wrong).
**Rejected.** A new public API to signal collapse (the existing `adsEnabled` notifier + `AdBlocked(adsDisabled)` state already carry it — nothing to add); animating the collapse (a deterministic `SizedBox` is simpler and no test requires animation); keeping a non-zero anchored placeholder "to avoid a downward shift when the ad loads" (the real emulator banner was SHORTER than the old estimate, so the old estimate caused the very gap it meant to prevent; a 50dp floor growing to the exact size is the honest minimum); reserving a guessed inline-adaptive height (wrong more often than right — zero, with an opt-in `placeholderHeight`, is correct).
**Consequences.** No API/semver change — a backward-compatible layout bug fix, no migration. Widgets now import `core/ad_block_reason.dart`. Guarded by focused widget tests (banner: 50dp floor not 90, loaded exact-size 60/100, inline zero, `placeholderHeight: 0`, adsDisabled overrides a non-zero placeholderHeight, synchronous collapse + handle drop + re-enable reload, no duplicate requests across rebuilds/toggles; native: collapse + recover; example: the disabled state removes the complete banner + native surfaces with the switch still accessible) — all neuter-verified fail-first (9 fail against the reverted widgets). The old device-height placeholder tests were updated to the new floor/zero behaviour.

## ADR-071 — never load while Mobile Ads init is in flight (incl. the forwardConsent path); close the disableAds() in-flight-load race; operationally-correct SSV docs (5.2.0)  ·  accepted (hardens ADR-032/033/061 init-settle; extends ADR-050 kill-switch)
**Context.** Three production-focused reliability findings, no redesign.
1. **Init-settle gate.** `AdFlow._settleRequestConfig()` returned `_requestConfigApplied || !_configFailurePolicyIsClosed`. For a fail-open config — and the `auto` default is fail-OPEN for a non-policy-sensitive config — that returned `true` even while the REAL `MobileAds.initialize()` future was still in flight (the bounded 2s init-join in `_applyRequestConfigOnce` having timed out). So a first-frame banner/native on a weak network or a mediation cold-start could dispatch an ad request before the SDK had initialized — an untagged/untest-flagged first request, and a step toward the ADR-028 platform-thread hazard. Only the fail-CLOSED (policy-sensitive) path was covered by a never-completing-init test; the fail-open/vacuous path was the gap.
2. **`disableAds()` in-flight-load race.** `recheckGate()` cannot drop an `AdLoading` controller (there is no handle yet), so a `disableAds()` (Remove-Ads) landing after a load passed the gate but before the SDK returned its handle ended with the late handle published as `AdLoaded` / kept warm — for every format. Widget-first mode hid some of it, but advanced controller usage and retained warm full-screen inventory made it a real lifecycle bug.
3. **SSV docs.** SSV was documented only as attach mechanics + fail-closed; nothing told integrators that `onReward`/attaching `userId`/`customData` is not proof, or what a valuable-reward backend must do.
**Decision.**
- **Init-settle:** `_settleRequestConfig()` now blocks (returns `false`, → `AdBlockReason.requestConfigNotApplied`) whenever `_initInFlight != null && !_initDone`, regardless of `RequestConfigFailurePolicy`. Fail-open takes effect only AFTER init has genuinely completed (a config attempted-and-failed-for-real). Init NOT-yet-started (a `forwardConsent` adopter defers init behind forwarding) is deliberately not "in flight" — the load flows past the config gate to the forwarding gate, which is what DRIVES forwarding to run (no regression for the fail-open-config adopter, whose forwarding retry is load-driven). Prompt recovery: the actual-init-completion hook in `_initializeAndConfigure` now kicks a config attempt DIRECTLY (bypassing the failure re-arm cooldown, since init-in-flight is a defer, not a failure to rate-limit), and `_applyRequestConfigOnce`, on success, calls `_recheckAll()` so blocked slots recover at once (mirrors `enableAds()`). Non-blocking init and the ADR-028 init→`updateRequestConfiguration` ordering are untouched; a never-completing init leaves slots in an honest `AdBlocked`, never `AdLoading`, never a request. **forwardConsent adopter path (release-gate follow-up):** the above covers a non-adopter (init in flight at the FIRST `_settleRequestConfig`). For a `forwardConsent` adopter the Ads SDK's init only STARTS after forwarding succeeds — AFTER the first config check ran, with init not yet in flight, so a fail-open config let that first check pass. `_settleConsentForwarding` then awaited `_initPipeline.timeout(_initTimeout)` and, on that timeout, PROCEEDED even with init still in flight, so a vacuous/fail-open placement fired a request post-timeout, pre-init. Fix: `_settleConsentForwarding` no longer waits on the pipeline (it only ensures init is kicked); `AdGate.loadBlockReason` RE-SETTLES request configuration AFTER the forwarding barrier (→ `requestConfigNotApplied` on false). That re-check is the single authority on "init done + config applied before any request" — bounded by the config gate's own 2s init-join, recovers on init completion, no duplicate config dispatch (the settle joins in-flight/applied state), a cheap no-op for a non-adopter. Forward-before-init preserved; the misleading pipeline-wait comment was removed.
- **In-flight-load race:** a new synchronous `AdGate.isEnabled` getter (a mirror of the injected `isEnabled` predicate, parallel to `AdGate.consentGeneration`). Every controller — banner, native, and the shared full-screen base (which covers interstitial/rewarded/RI/app-open; none overrides `load()`) — re-reads `!_gate.isEnabled` SYNCHRONOUSLY in the same turn it would publish `AdLoaded`, and if ads were disabled while the request was in flight it disposes the returned handle, never installs it, and reports `AdBlocked(AdBlockReason.adsDisabled)`. Because it is a pure bool read (no fallible collaborator), a transient `internalError` can never wrongly drop good inventory — the existing asymmetric "indeterminate never drops a live ad" policy is preserved, and the consent-generation invalidation is untouched (it handles consent staleness; `disableAds()` does not bump the generation, which is exactly why the explicit enabled re-check is required).
- **SSV docs:** README rewarded section + `ServerSideVerification`/`OnUserEarnedReward`/`RewardedConfig.ssv`/`RewardedInterstitialConfig.ssv` dartdoc now state `onReward` is a client-side signal (not proof), that attaching does not prove backend verification, and the backend duties (verify `signature`/`key_id`, validate user/ad-unit/reward/customData, idempotent `transaction_id`), the two fulfillment strategies (grant-then-reconcile vs. wait-for-verified-callback), the don't-double-grant warning, and a link to Google's Flutter SSV guide.
- **App Open failed-load leak (upstream):** re-verified against the installed `google_mobile_ads` 9.0.0 source — the asymmetry still exists exactly as ADR-048 / RESEARCH §3 describe (the `AppOpenAd` failed-load branch omits `ad.dispose()`, and its failure callback carries no ad reference the seam could dispose). Low-severity, process-bounded, unfixable from outside the seam. The honest note is retained; no fragile internal-import/reflection workaround, and no patch expansion.
**Rejected.** Using the async `AdGate.showBlockReason` for the in-flight re-check (its `canRequestAds` await reopens the exact check-then-await-then-write race of ADR-024 — a `disableAds()` during that await is missed; a pure synchronous bool decided adjacent to the `AdLoaded` write is the only race-free option); a flag-then-recheck approach that publishes `AdLoaded` briefly then drops it (violates "never publish AdLoaded", and leaves a window where a state listener / immediate `show()` sees the dead-to-be handle); making the config gate block even when init is NOT started (would starve a fail-open-config forwarding adopter, whose forwarding is driven only by loads reaching the forwarding gate); a new `AdLoadState`/enum/state-machine (breaking in a patch, and unnecessary — `AdBlocked(adsDisabled)` + `requestConfigNotApplied` already exist); a version-pinned regression test for the upstream App Open leak (fragile against a pub-cache internal; the doc-note + manual re-check on plugin bumps is the right weight); a migration section (nothing to migrate).
**Consequences.** Backward-compatible **minor 5.2.0** — NOT a patch. The release adds exactly one public symbol: the additive, internal-facing getter `AdGate.isEnabled` (a concrete exported DI class; additive, non-breaking, mirrors `AdGate.consentGeneration`). SemVer honesty: `AdGate` is exported through the public barrel, so a new non-underscore member is a production-public API addition, which is a MINOR bump, not a patch — an earlier draft mislabelled it 5.1.2. The getter is kept (it is the exact, simple, race-free primitive for the same-turn Remove-Ads invariant, and parallels `consentGeneration`); `@internal` was deliberately NOT used to pretend an exported member is not API. No removals, no signature/enum/default changes; every existing call site compiles unchanged and there is **no migration**. Guarded by: `request_config_policy_test.dart` (+1 — vacuous/fail-open under a held init sends NO request, settles to `AdBlocked(requestConfigNotApplied)`, then applies config + recovers on completion), `consent_forwarding_test.dart` (+1 — a forwardConsent adopter whose forwarding STARTS a held init after the first config check sends NO request past the init-wait timeout, then recovers + loads exactly once), `inflight_disable_race_test.dart` (+2 — banner & native via the real `disableAds()`), `inflight_permission_recheck_test.dart` (+2 — the shared full-screen base via a mutable-`isEnabled` gate, plus the transient-`internalError`-does-not-drop regression that had zero prior coverage). All five behavioural tests were confirmed fail-first against the unmodified controllers/facade/gate. Verified: `dart format` clean, `flutter analyze` clean, full suite green (543), pana 160/160, dry-run 0 warnings, Android + iOS example builds (see PROGRESS "How to verify").

## ADR-072 — cached-consent startup fast path; final full-screen dispatch guard (5.2.1)  ·  accepted (extends ADR-035 consent-as-a-process; extends ADR-024/050/071 same-turn revocation)

**Context.** Two windows survived 5.2.0. (A) **Slow consent for a returning user.** `UmpConsentGateway._run()` resolves `canRequestAds()` only after `requestConsentInfoUpdate()` + the form flow finish, and `AdFlow._settleConsent()` joined that whole in-flight op — so a returning user whose PREVIOUS session already made `canRequestAds()` true lost all serving (first-frame banner/native, full-screen preloads, cold App Open readiness) until this launch's update completed or hit the 30s timeout, on exactly the weak/intermittent networks this package targets. Google's UMP guidance: check `canRequestAds()` right after DISPATCHING the update, because valid consent may already exist from the previous session. (B) **Final full-screen dispatch boundary.** `showEngine()` claims the coordinator + writes `AdShowing`, then `await`s `showBlockReason()` and `_caps.canShow()` before the irreversible `handle.show()`. A `disableAds()` / consent mutation landing during those awaits is deliberately skipped by `_recheckAll()` (it does not touch `AdShowing`), and a slow cap-store hydration can let the ad age past `maxAdAge` — so the previously-captured handle could be dispatched despite being revoked or stale (interstitial/rewarded/app-open; the RI intro path already re-validated).

**Decision.** Both fixes are entirely INTERNAL — **no public API, no default change** (patch 5.2.1). (A) `_settleConsent` gains a cached-consent fast path: when eligible it reads the cheap live `_sdk.canRequestAds()` and, if a returning user's cached consent already permits ads, returns immediately instead of joining the slow flow — the gate's own next-step `canRequestAds()` read still confirms, the slow flow keeps running and publishes its final result, and a downgrade to `false` drops the early inventory (via each controller's live gate check). Eligibility (`_consentFastPathEligible`, computed in `initialize`) requires: the facade OWNS the default gateway (so the info update is dispatched at startup, deep before the fast path fires in the load's async chain — no gateway change needed), NO client-driven ATT primer (so serving on cached consent can never precede a required ATT decision), and NO `forwardConsent` adopter (whose loads are fail-closed on the forwarding barrier regardless — the fast path would give no benefit and only risk serving before forwarding). The `_runConsent` completion re-points forwarding (bumps the consent generation) only when there IS a forwarder — a non-adopter's initial/retry settle must NOT bump, or it would invalidate the perfectly good ad the fast path just served (settling to the SAME answer) and force a wasteful reload; a real later MUTATION still invalidates via `_afterConsentMutation`. (B) `showEngine` adds a FINAL synchronous guard in the same turn as `handle.show()`: `_disposed`, `!_gate.isEnabled` (→ drop, `AdBlocked(adsDisabled)`, never left warm — mirrors `recheckGate` which could not touch `AdShowing`), stale consent generation (→ discard+reload), `isExpired` (→ discard+reload). No new network/consent flow and no async cap recompute at the boundary (all reads are synchronous pure facts); coordinator balance, exactly-once `show()`, reward semantics, the RI intro and transient-`internalError` behavior are unchanged.

**Consequences.** Patch **5.2.1** — verified complete public API delta is EMPTY (only two internal files change: `ad_flow.dart` fast path/reconcile, `full_screen_ad_controller_base.dart` guard; `AdFlow._` gained a private required param; the gateway is untouched). No removals, no signature/enum/default changes, no migration. Guarded by: `consent_fastpath_test.dart` (+3 — cached-true serves while the update is held with no duplicate load; cached-false does NOT serve early; the forwardConsent barrier stays fail-closed) and `show_dispatch_guard_test.dart` (+3 — ads-disabled / consent-generation-change / expiry each cross while the cap check is held → `show()` returns false, zero `handle.show()` calls, coordinator released, not left warm). All confirmed fail-first against the unmodified facade/base. Also fixed a PRE-EXISTING flake in `consent_forwarding_test.dart`'s 5.2.0 init-wait test (asserted a momentary state against a jitter-randomized gate-recheck; now asserts the durable facts — no request, honest block reason, never served — matching the "hung forwarder" test's pattern). Docs reconciled: README + `AppOpenHandle` dartdoc (App Open trigger modes, not "warm-start only"), and the runtime-SSV helper doc (load-time attach fails the load CLOSED for a configured SSV, not silent best-effort). Verified: `dart format` clean, `flutter analyze` clean, full suite green (549), pana 160/160, dry-run 0 warnings, Android + iOS example builds (see PROGRESS). Upstream App Open failed-load leak (ADR-048) unchanged.

**Addendum (5.2.2) — downgrade must invalidate inventory IN FLIGHT.** The 5.2.1 reconcile above ("a downgrade to `false` drops the early inventory via each controller's live gate check") was incomplete: `_recheckAll` reaches a controller's `recheckGate`, which drops an already-`AdLoaded` ad but NO-OPS on `AdLoading`/`AdShowing`. So a fast-path load whose SDK request was still in flight at the downgrade, and a full-screen show already waiting at an async pre-show boundary, were NOT dropped — the completing load installs `AdLoaded` and the show can dispatch, because the completion generation check and the final show-dispatch guard both key off the consent generation, which (for a non-forwarder) nothing bumped. Fix (internal, no public API, patch 5.2.2): a private flag `_consentFastPathServed` records that the fast path was ACCEPTED; on a downgrade (`!open && served`) `_runConsent` bumps `_consentGeneration` BEFORE `_recheckAll` — using the existing generation mechanism directly, NOT `_invalidateConsentForwarding` (which is for forwarding apps; the non-adopter same-answer no-bump rule from 5.2.1 stands). The in-flight load's own completion check and the show-dispatch guard then reject the now-stale generation (dispose, never `AdLoaded`, no impression/show, honest blocked state, no dup/storm, balanced coordinator). Separately, `_settleConsent` now publishes `_canRequestAdsNotifier.value = true` the moment the fast path is accepted — `AdFlow.canRequestAds` is the documented LIVE reactive value and previously stayed `false` while ads were already serving; the flow reconciles it (to `false` on a downgrade). `whenReady` unchanged. Guarded by `consent_fastpath_test.dart` (+1, fail-first + neuter-verified: the generation bump AND the notifier publish are each load-bearing) and the existing `show_dispatch_guard_test.dart` generation case (proves the guard rejects the bumped generation). Verified: format/analyze clean, full suite green (550), dry-run 0 warnings.

## ADR-073 — anchored adaptive banners are sized from the PLATFORM's post-load size; per-format sample ad units; opt-in opaque slot background (5.3.0)  ·  accepted (corrects ADR-003's premise; completes the loaded-state half ADR-070 left open)

**Context.** Issue #15 reported an `AdFlowBanner` occupying far more vertical space than the ad it showed, with the app's own surface visible around a narrow, short creative. ADR-070 investigated the same 468×60 creative on the same Pixel emulator, fixed the **pre-load** reservation, and concluded "loaded banners already follow `handle.dimensions` correctly". That conclusion was wrong, for a reason nothing in the repo could have predicted without reading the plugin's codec. Three stacked causes, verified from source (plugin Dart + Android Java + iOS ObjC, and a decompile of `play-services-ads-api` 25.3.0, the version `google_mobile_ads` 9.0.0 pins at `android/build.gradle:71`):

1. **The plugin cannot round-trip the "large" bit — so Dart and the platform disagree about the height.** `AdSize.getLargeAnchoredAdaptiveBannerAdSize` genuinely resolves the LARGE height: it dispatches `AdSize#getLargeAnchoredAdaptiveBannerAdSize`, which the native handlers service with `isLarge = true` (`GoogleMobileAdsPlugin.java:536-549`; `FLTGoogleMobileAdsPlugin.m:535-545`). But the resulting `AnchoredAdaptiveBannerAdSize` carries **no `isLarge` field** (`ad_containers.dart:331-346`), and the codec writes only `(orientation, width)` — the resolved height and the largeness are both dropped (`ad_instance_manager.dart:1320-1334`). Both native decoders then rebuild it with a hardcoded `/* isLarge = */ false` (`AdMessageCodec.java:276-281`; `FLTGoogleMobileAdsReaderWriter_Internal.m:247-254`), which selects the **classic** factory (`FlutterAdSize.java:83-88`; `FLTAd_Internal.m:98-106`), and *that* is the size handed to `AdView.setAdSize()` / `[[GADBannerView alloc] initWithAdSize:]`. Net: the ad request and the native ad view are CLASSIC-sized while Dart holds the LARGE number. Decompiled formulas — classic `h = max(50, min(widthBand(w), min(90, round(0.15·screenHdp))))`, large `h = max(50, min(max(100, round(w/320·100)), min(150, round(0.20·screenHdp))))` — put that at **133dp held vs 67dp rendered** on the reporter's device (Pixel 10 Pro AVD: 1280×2856 @ density 3.0 = 426×952dp). ad_flow took `handle._ad.size` unconditionally and gated the `getPlatformAdSize()` re-query to inline adaptive only, so `AdFlowBanner` hard-sized a `SizedBox` to the Dart number: a **~66dp band that exists on every anchored banner, whatever creative serves**. Flutter's platform-view layout is one-directional (every platform-view render box is `sizedByParent` with `computeDryLayout => constraints.biggest`; the engine then forces the embedded native view to that box), the plugin's `AdWidget` has no intrinsic size, and Google's `BaseAdView.onLayout` centres its single creative child at the child's own measured size — so the band is split symmetrically and left **unpainted**, showing the app's surface through the transparent slot.
2. **The Android sample banner unit was the wrong FORMAT.** Google publishes a different demo unit per banner format. `TestAdUnitIds.banner.android` was `…/6300978111` — the **Fixed Size Banner** unit, which only ever answers with fixed IAB creatives (320×50, 320×100, 468×60: exactly the labels in the report) — while the default kind is `anchoredAdaptive` and `testMode` forces the sample ID over any publisher ID. The iOS entry was already the adaptive unit (`…/2435281174`), so the pair was internally inconsistent and the defect was Android-only. Google's own sample uses `…/9214589741` (`example/lib/anchored_adaptive_example.dart:64-66`).
3. **By design, and unaddressed:** an adaptive slot is anchored to its WIDTH. When a smaller creative fills it, the SDK centres it and nothing paints the surround. Google's anchored-adaptive guidance is to give the ad view an **opaque background** for this case (its own sample hardcodes `Container(color: Colors.green)`); ad_flow offered publishers no way to supply one.

**ADR-003's premise was wrong; its decision still stands.** ADR-003 adopted `getLargeAnchoredAdaptiveBannerAdSize` on the stated basis that "only the adaptive-banner methods were renamed". They are not a rename — the two families dispatch different channel methods and only the QUERY path honours largeness. This ADR amends that context. It does **not** supersede the decision: because the encoder writes only `(orientation, width)`, both Dart factories produce a byte-identical wire message and an identical native request, so switching to `getCurrentOrientationAnchoredAdaptiveBannerAdSize` would change nothing that is requested or rendered — and that method is the `@Deprecated` one, removable in plugin 10.

**Decision.**
- **Seam (the fix).** `_finishBannerLoad` resolves the handle's dimensions from `getPlatformAdSize()` for **both** adaptive kinds, not just inline. Failure semantics stay ASYMMETRIC and that asymmetry is the load-bearing part: **inline** has no requested height to fall back on (its `AdSize` is literally height 0), so a null/failed query remains a failed initial load and a keep-the-last-size no-op on auto-refresh (ADR-048 unchanged); **anchored** has a concrete, renderable requested height, so a null, zero or throwing query falls back to it, completes the load normally, and **never** disposes a billable ad. On the reporter's device the slot goes 133dp → 67dp and the structural band disappears.
- **Per-format sample units.** `TestAdUnitIds.adaptiveBanner` (android `…/9214589741`, ios `…/2435281174`) and `TestAdUnitIds.fixedBanner` (android `…/6300978111`, ios `…/2934735716`), selected by `BannerKind` via `TestAdUnitIds.forBannerKind`. `AdFlowConfig.bannerAdUnitId` takes an optional `kind:`, and `AdFlow.banner()` resolves from the PER-PLACEMENT override's kind so a `BannerConfig` override gets the matching unit. `TestAdUnitIds.banner` is retained as an alias of `adaptiveBanner` (the default kind's unit) so no existing const reference breaks. Production is untouched — the publisher supplies the ID.
- **`AdFlowBanner.backgroundColor`** (nullable, default null = today's behaviour): an opaque colour painted as a `ColoredBox` **under** the ad and under the pre-load placeholder, inside the existing box. Strictly behind — never a `Stack` above, never a clip, scale or overlay (occluding a creative is a policy violation, and a widget test asserts both the ancestry and the absence of any `Stack`). Ignored while ads are disabled, like `placeholderHeight`: a Remove-Ads banner must leave no coloured strip behind.
- **Deliberate non-change: no standard-vs-large knob.** Source proves it would be inert today (identical wire message), so it would mislead publishers into thinking they can pick a format. Revisit only if the upstream `isLarge` round-trip is fixed. The docs state the limitation plainly.
- **Ground truth corrected.** `RESEARCH.md` §3 still carried the CLASSIC bounds ("minimum 50dp; maximum `min(90dp, 15% of device height)`") and the claim that there is "no pure-width formula" — both wrong for the API the seam calls, and the reason this survived ADR-070. Replaced with both decompiled formulas and the codec asymmetry.

**Rationale.** Attacks the mechanism (Dart height vs native height) rather than the symptom, in the one file allowed to import `google_mobile_ads` (invariant 8 intact). It does not change what is requested, so there is no fill, revenue or policy change. It also *improves* the ADR-070 posture: the pre-load 50dp floor now grows to ~67dp instead of ~133dp, so the layout shift roughly halves. The residual letterboxing of an undersized creative is by design and cannot be sized away — an adaptive slot is width-anchored — so the opaque background is the correct, Google-prescribed remedy rather than a rendering trick.

**Rejected.** Swapping the seam to the deprecated classic call (inert — identical wire message — and parks the package on an API removable in plugin 10); sizing the box to the SERVED creative (verified impossible: `getPlatformAdSize()` returns `adView.getAdSize()` / `bannerView.adSize`, i.e. the size the native view was CONSTRUCTED with, and the plugin's only served-size feedback channel, `onFluidAdHeightChanged`, is `FluidAdManagerBannerAd`-only and unavailable to AdMob `BannerAd`; `ResponseInfo` carries no dimensions); clipping/scaling/overlaying the creative to hide the band (policy violation); changing the default `BannerKind` (inline adaptive is the wrong format for a bottom-anchored placement, and the issue's own report is a bottom-bar layout); a `BannerConfig.backgroundColor` (would drag `dart:ui`'s `Color` into the otherwise Flutter-free config layer — this is presentation, so it belongs on the widget); the issue's proposed `BannerPlacement`/`BannerLayoutPolicy` API (the real defect was a sizing bug, not a missing policy engine; once the box matches the platform there is no placement-specific decision left to make).

**Consequences.** Backward-compatible **minor 5.3.0**. Additive public API only: `TestAdUnitIds.adaptiveBanner` / `.fixedBanner` / `.forBannerKind`, `BannerConfig.defaultKind`, an optional `kind:` on `AdFlowConfig.bannerAdUnitId`, and `AdFlowBanner.backgroundColor`. No removals and no signature changes; every existing call site compiles unchanged and there is no migration. **Behaviour-visible in two places, both intended:** an anchored banner's box now matches what the SDK actually renders (typically about half its previous height on a phone), and `testMode` on Android now serves correctly-sized adaptive test creatives. Guarded by `gma_ad_sdk_test.dart` (+6 — platform size wins over the requested one; null / throwing / zero-height queries each fall back and still complete the load without disposing; an auto-refresh resizes the live handle and notifies; a fixed banner never pays for the round trip), `ad_flow_config_test.dart` (+3 — kind→unit selection for all three kinds, the documented IDs pinned, per-placement kind overriding the global one) and `ad_flow_banner_test.dart` (+4 — no colour by default; painted behind both the loaded ad and the placeholder without adding height; ad renders ON TOP with no `Stack` anywhere; Remove-Ads leaves no strip). Full suite green (563), `flutter analyze` clean. **Upstream:** the `isLarge` round-trip is a `googleads-mobile-flutter` defect (still unfixed on main) — the encoder must carry the flag and both decoders must stop hardcoding `false`; the native factories already accept it and the query path already honours it, so the asymmetry is one field wide. Until it lands, no Flutter app can actually request Google's large anchored adaptive format; every "large" request degrades to classic. This ADR makes ad_flow honest about that, it does not recover the lost inventory. **Not yet done (verify-by-running):** on-device confirmation that a Pixel 10 Pro portrait anchored banner reports ~67dp, on both Android and iOS — everything above is source-derived.
